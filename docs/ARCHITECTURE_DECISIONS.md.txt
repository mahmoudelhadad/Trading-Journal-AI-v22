# AD-004

## Title

Independent storage-cutover feature flag (VITE_STORAGE_CUTOVER_ENABLED).

---

## Status

Approved

---

## Date

2026-08-02

---

## Context

Leader election originally lived exclusively inside startSyncEngine(),
itself gated behind VITE_SYNC_ENGINE_ENABLED. The §13 Step 6 storage
cutover also requires leader election (sub-step 0: "elected by the same
Web Lock that governs ongoing sync"). Reusing the Sync Engine's flag
would have made it impossible to roll out the LocalStorage -> IndexedDB
migration without also enabling real cloud sync network activity against
the user's Supabase project.

---

## Decision

Introduce a second, independent flag, VITE_STORAGE_CUTOVER_ENABLED, read
by isStorageCutoverEnabled() (services/syncEngineSetup.ts). Defaults to
OFF. Governs only whether the cutover is registered as a leader
callback; has no effect on the Sync Engine.

---

## Consequences

- The two rollout decisions (storage medium vs. cloud sync) can be made
  independently.
- Both flags can enable leader election, which must still resolve to
  exactly one Web Lock acquisition — enforced structurally by
  startLeaderElection()'s shared idempotent guard (AD-005), not by this
  flag itself.
- An operator can enable the cutover for a cohort without those users'
  data ever leaving the device.

---

## Alternatives Considered

- Reuse VITE_SYNC_ENGINE_ENABLED for both. Rejected: couples two
  unrelated rollout decisions, and the spec's only feature-flag
  recommendation (§13 Step 5's "gate Step 5 behind a feature flag") is
  scoped to Step 5 only; §15.8 assigns Step 6 a different mitigation
  (the completion-marker/verify/restart protocol), not a flag.

---

## Rejected Alternatives

Single shared flag — rejected per above.

---

## Spec References

SYNC_ARCHITECTURE_SPEC.md §13 Step 6 sub-step 0; §13 Step 5's rollout
note; §15.8.

---

## Revisit Only If

The two rollout tracks are later judged safe to merge (e.g. once both
have shipped to 100% for some time), or a real deployment need arises to
tie them together.

# AD-005

## Title

Leader election extracted from the Sync Engine into a standalone
coordination layer.

---

## Status

Approved

---

## Date

2026-08-02

---

## Context

AD-004 requires the cutover to acquire leadership independently of the
Sync Engine, but §5.4 and §13 sub-step 0 both require exactly one Web
Lock acquisition per tab regardless of how many subsystems need
leadership.

---

## Decision

src/sync/syncEngine.ts exposes startLeaderElection(options) /
stopLeaderElection(), a coordination-only layer: it registers a callback,
ensures the Cross-Tab Coordinator's coordinatorStart() has run exactly
once (via an idempotent guard), and returns. It creates no Scheduler, no
periodic timer, no Online Monitor, no online/visibilitychange/dirty-ping
listener, performs no network I/O, and does not touch the Sync Engine's
own `started`/`engineDeps` state. startSyncEngine() itself now registers
its own "app start" trigger through this same layer.

---

## Consequences

- Any number of subsystems (today: the cutover and the Sync Engine) can
  request leadership; the browser still grants exactly one Web Lock.
- Registration order is load-bearing and is now a documented contract:
  callbacks fire in registration order, each awaited before the next.
- stopSyncEngine() now internally calls stopLeaderElection(); a caller
  using leader election without the Sync Engine can still tear down
  independently.

---

## Alternatives Considered

- A second, parallel Web Lock name for the cutover. Rejected: directly
  violates "the same Web Lock" (sub-step 0) and would allow two
  independent leaders on one tab-set simultaneously.
- Leave leader election inside startSyncEngine() and have the cutover
  call startSyncEngine() with a no-op dependency set. Rejected: would
  spin up a real SchedulerCore and its triggers merely to piggyback on
  leadership, contradicting the Sync Engine's own idempotent
  single-instance discipline (§5.4) and doing real work the cutover does
  not need.

---

## Rejected Alternatives

Both alternatives above — rejected per stated reasons.

---

## Spec References

SYNC_ARCHITECTURE_SPEC.md §5.3, §5.4, §13 Step 6 sub-step 0.

---

## Revisit Only If

A third subsystem needs leadership and the current registration-order
contract proves insufficient to express its ordering requirements.

# AD-006

## Title

Set-based idempotent leader-callback registration.

---

## Status

Approved

---

## Date

2026-08-02

---

## Context

contexts/AuthContext.tsx's effect re-runs whenever the Supabase `session`
object identity changes (e.g. on every token refresh). Without
idempotent registration, each re-run would register the cutover callback
again, and — depending on dispatch timing — could execute it more than
once.

---

## Decision

leaderCallbacks changed from an Array to a Set, keyed by callback
reference. startLeaderElection() checks `leaderCallbacks.has(callback)`
before adding; a duplicate registration is a complete no-op. A Set's
iteration order matches insertion order, so registration ordering is
preserved without extra bookkeeping.

---

## Consequences

- Registering the same function reference any number of times executes
  it exactly once.
- Callers that want idempotency MUST pass a stable, module-scope
  function reference — an inline arrow is a new reference on every call
  and defeats the dedupe. contexts/AuthContext.tsx's
  runCutoverAsLeader is declared at module scope specifically for this
  reason; this constraint is documented at the call site.

---

## Alternatives Considered

- A boolean "already registered" flag per caller, managed by each
  caller. Rejected: pushes the responsibility out to every call site
  instead of guaranteeing it centrally.
- Dedupe by a caller-supplied string key instead of function identity.
  Rejected: adds a second thing callers must get right (a unique,
  stable key) for no benefit over reference identity, which is already
  free in JavaScript.

---

## Rejected Alternatives

Both above — rejected per stated reasons.

---

## Spec References

None directly (implementation detail); supports AD-005's coordination
layer and SYNC_ARCHITECTURE_SPEC.md §5.4's "must be idempotent"
discipline.

---

## Revisit Only If

A caller genuinely needs to register logically-different callbacks that
happen to share a function reference (not currently possible in this
codebase's usage).

# AD-007

## Title

Epoch-based cancellation of queued leader callbacks.

---

## Status

Approved

---

## Date

2026-08-02

---

## Context

stopLeaderElection() resetting the shared dispatchChain variable only
replaces the module's reference to it — a chain already built continues
running to completion independently. Testing proved a callback queued
behind a slow one still executed after stopLeaderElection() had
returned. This phase's scope explicitly forbids introducing any new
locking or synchronization primitive (e.g. AbortController).

---

## Decision

A plain integer, dispatchEpoch, incremented by stopLeaderElection().
Each enqueue captures the epoch in effect at the moment it is queued;
the wrapper re-checks it immediately before invoking the callback and
is a no-op if the epoch has since changed.

---

## Consequences

- Every callback still queued (not yet started) at the moment
  stopLeaderElection() is called becomes a guaranteed no-op.
- No new synchronization primitive, no lock, no abort mechanism —
  satisfies the explicit constraint for this phase.
- Disclosed, accepted residual: a callback already EXECUTING when
  stopLeaderElection() is called cannot be interrupted. True
  cancellation of in-flight work would require an abort mechanism that
  does not exist in this codebase (MIGRATION_NOTES.md AN-015 item 3) and
  which this phase was explicitly forbidden from adding.

---

## Alternatives Considered

- AbortController per callback. Rejected: explicitly forbidden by this
  phase's scope ("Do NOT introduce any new synchronization primitive").
- Clearing leaderCallbacks alone, without an epoch. Rejected: does not
  address an already-queued (already-chained) callback, since the
  chain's `.then()` continuations are already scheduled independently
  of the Set.

---

## Rejected Alternatives

AbortController — rejected, out of scope by explicit instruction.

---

## Spec References

None directly. Interacts with, but does not attempt to fully solve,
SYNC_ARCHITECTURE_SPEC.md §3.5 step 1's abort requirement (AN-015 item 3,
still deferred in full).

---

## Revisit Only If

AN-015 item 3 (abort in-flight requests on sign-out) is taken up as its
own approved phase — at that point the residual "cannot interrupt an
executing callback" gap should be re-evaluated against whatever abort
mechanism is introduced.

# AD-008

## Title

Stamping strategy: one implementation, two call sites, before the
cutover's snapshot.

---

## Status

Approved

---

## Date

2026-08-02

---

## Context

SYNC_ARCHITECTURE_SPEC.md §13 sub-step 2 requires the copy to be "in the
Step 3 shape (sync metadata included)". main.jsx already calls
runSyncMetadataStampingPass() unconditionally on every load. Moving that
call out of main.jsx (a literal reading of an earlier instruction) would
have stopped stamping from running at all whenever the cutover flag is
off — a real regression for any user with legacy unstamped data,
since loadLists()/loadSettings() return null for unstamped singletons
and their hooks fall back to hard defaults.

A first implementation attempt placed the cutover's stamping call
immediately before the FINAL readSource() (the re-check), matching an
initial literal instruction. Testing proved this placement provided no
real safety net: every IndexedDB business store keys on syncId, so an
unstamped record fails the copy phase (`putAll`) before that placement
is ever reached.

---

## Decision

Keep main.jsx's call exactly where it is (preserves marker-absent
behavior identically). Additionally call the SAME single
runSyncMetadataStampingPass() implementation (src/sync/stamp.ts) inside
runStorageCutover(), immediately BEFORE the initial readSource()
snapshot — i.e. before the copy phase, not after it. The function is
idempotent at record granularity (skips already-stamped records, writes
nothing if nothing changed), so on the common path (main.jsx already
stamped before React rendered) the cutover's call is a no-op.

---

## Consequences

- The cutover now has a genuine safety net for legacy unstamped data
  reaching it by any other route than main.jsx's normal startup call —
  verified directly: previously-failing unstamped trades/accounts/
  lists/settings now complete successfully, fully stamped.
- Exactly one stamping implementation exists (src/sync/stamp.ts); no
  logic duplicated.
- main.jsx's call becomes a pure no-op read after the cutover has run
  (marker present) — explicitly accepted as fine, since it performs no
  write in that state.

---

## Alternatives Considered

- Stamp only inside the cutover, remove main.jsx's call. Rejected:
  regression while the cutover flag is off — see Context.
- Stamp immediately before the re-check (first attempt). Rejected:
  proven unreachable for unstamped data by direct testing (copy phase
  fails first).
- A stamping-specific flag/condition gating whether the cutover stamps.
  Rejected: explicitly forbidden ("Do not add any flags, conditions").

---

## Rejected Alternatives

Both non-chosen placements above — rejected per stated reasons, the
second one only after being implemented and empirically disproven.

---

## Spec References

SYNC_ARCHITECTURE_SPEC.md §13 Step 3 (the original stamping pass), §13
Step 6 sub-step 2 ("in the Step 3 shape").

---

## Revisit Only If

The stamping pass's own idempotency contract (src/sync/stamp.ts) ever
changes, or a future phase decides main.jsx's call should be removed for
an unrelated reason (e.g. an async pre-render gate is introduced
elsewhere).

# AD-009

## Title

Source re-check strategy: Option A (re-read and restart), no lock.

---

## Status

Approved

---

## Date

2026-08-02

---

## Context

Between the cutover's LocalStorage snapshot and the completion-marker
write, another tab's hooks could write new data to LocalStorage. Once
the marker exists, IndexedDB becomes authoritative and that write would
never be copied — a silent, permanent data loss (Principle 1). A Web
Lock-based write barrier (Option B, previously discussed) would close
this window completely but was explicitly rejected as introducing new
application-visible behavior (delaying or blocking follower-tab writes
during the cutover) not described anywhere in the specification.

---

## Decision

Immediately before writing the completion marker, re-read LocalStorage
via the existing readSource() and compare it (via JSON.stringify) against
the original snapshot. If they differ, restart the entire attempt from
the top (discard IndexedDB business data, re-stamp, re-snapshot,
re-copy, re-verify), bounded at MAX_CUTOVER_ATTEMPTS (3). If attempts are
exhausted, return a distinct {kind:'source_changed'} outcome; the marker
is not written, and the cutover simply retries on the next load — the
same effect as any other non-completing outcome (sub-step 5).

---

## Consequences

- Narrows the unsafe window from "the entire copy+verify duration" to
  "the time between the re-check read and the marker write" — verified
  directly: a concurrent write injected mid-copy was detected, the
  cutover restarted, and the write is present in the final state.
- Does not fully close the window (a write landing in the few
  instructions between the re-check and the marker write is still
  possible in principle) — disclosed, not solved, per the explicit
  decision to use Option A only.
- No new synchronization primitive of any kind; cannot block or delay a
  writer in any tab, so it introduces no new application behavior.
- Bounded attempts prevent an unbounded retry loop under continuous
  concurrent writing — verified: exhaustion after 3 attempts leaves
  LocalStorage untouched and the marker unwritten.

---

## Alternatives Considered

- Option B: a Web Lock-based write barrier requiring writers to
  acquire a shared lock. Rejected: introduces new application behavior
  (writers can be delayed/blocked during a cutover) with no basis in
  the specification, and was explicitly excluded from this phase's
  scope.
- Unbounded retry until the source stabilizes. Rejected: no bound on
  worst-case duration under continuous writing; the bounded-then-defer
  approach achieves the same eventual outcome (sub-step 5's normal
  retry-on-next-load) without an open-ended loop.

---

## Rejected Alternatives

Web Lock write barrier (Option B) — rejected, out of scope by explicit
instruction. Unbounded retry — rejected per stated reasons.

---

## Spec References

SYNC_ARCHITECTURE_SPEC.md §13 Step 6 sub-step 5 (restart-from-scratch
semantics); Principle 1 (no silent data loss).

---

## Revisit Only If

The residual, disclosed micro-window between re-check and marker write
is later judged unacceptable, at which point Option B (or an equivalent
mechanism) would need its own dedicated review and approval.

# AD-010

## Title

Local-persistence notice architecture (§3.4 blocking notice).

---

## Status

Approved

---

## Date

2026-08-02

---

## Context

SYNC_ARCHITECTURE_SPEC.md §3.4 requires two conditions be surfaced to
the user as "a distinct, blocking notice — never folded into the
ordinary 'sync pending' indicator": a failed local write (in particular
quota exhaustion, which must direct the user toward a corrective action
rather than offering a retry that cannot succeed), and a tab whose
IndexedDB connection was force-closed by a version upgrade in another
tab (which must prompt a reload).

---

## Decision

A single last-event bus, services/localPersistenceEvents.ts, is the
sole aggregation point for both conditions. It self-wires to the
already-existing G-1 subscription API
(onIndexedDbVersionChangeForcedClose) at module load, so importing it is
sufficient to forward every future force-close. A single React
component, components/LocalPersistenceNotice.tsx, subscribes and renders
a Modal (not a toast, since §3.4 says "blocking") with condition-specific
content: quota failures get corrective guidance and no retry button;
other save failures name their source; a force-closed connection offers
only a Reload action and cannot be backdrop-dismissed (since every
subsequent local operation throws until reload). Built and wired in full
in one phase rather than as a placeholder revisited later.

---

## Consequences

- Exactly one notice can be active at a time — a second failure while
  one is displayed overwrites rather than queues, since only one is
  ever actionable.
- 6g-2 required zero changes to this layer; wiring the cutover's own
  failure modes into it (a later phase) only requires new callers of
  reportLocalPersistenceFailure.
- Verified end-to-end with a genuine browser versionchange event (not a
  simulated call), and with a real IndexedDB write failure surfacing the
  correct errorKind.

---

## Alternatives Considered

- A generic single-message notice with no condition-specific content.
  Rejected: fails §3.4's "must direct the user toward a corrective
  action" requirement for the quota case specifically.
- Build only what BD-1/BD-2 needed immediately, defer the rest.
  Rejected in favor of building the full structure once, since a
  partial build would have been revisited and reshaped in the very next
  phase — explicitly rejected as an unnecessary intermediate
  architecture.

---

## Rejected Alternatives

Generic single-message notice — rejected per stated reason.

---

## Spec References

SYNC_ARCHITECTURE_SPEC.md §3.4 (both the quota-exhaustion and the
version-upgrade requirements).

---

## Revisit Only If

A third distinct local-persistence condition needs surfacing (at which
point the last-event, single-notice model should be re-examined for
whether it still suffices), or read failures need their own distinct
notice kind (currently labelled identically to save failures — a known,
disclosed, low-severity gap).

# AD-011

## Title

backupService migration: four sections routed through the resolver.

---

## Status

Approved

---

## Date

2026-08-02

---

## Context

backupService.ts composes ten LocalStorage-backed sections
(trades, accounts, lists, settings, propRules, savedFilters,
checklistTemplates, checklistCompletions, customFieldDefs,
customFieldValues) into one backup/restore format. Four of these
(trades, accounts, lists, settings) are the sections migrated to the
resolver in Phase 6f; once the cutover flip occurs, reading them via
storage.js directly would silently read the frozen LocalStorage rollback
copy instead of the authoritative store.

---

## Decision

Only the four resolver-backed sections import their load/save functions
from services/localDatabase.js; the other six remain on services/
storage.js unchanged. BackupSection.load/save widened to
MaybePromise<...> (reusing src/sync/localStores.ts's existing type, not
a new one). buildBackup/restoreBackup and every function built on them
(downloadBackup, restoreBackupFromJSON, createRestorePoint,
restoreFromPoint, maybeCreateAutoBackup) became async; every consumer
(BackupPanel.tsx, SyncConflictReview.tsx, useRestorePoints.ts,
RestorePointsPanel.tsx, SettingsModal.tsx) updated to await and handle
rejections. listRestorePoints/deleteRestorePoint remain synchronous —
RESTORE_POINTS was never part of the Step 6 migration.

---

## Consequences

- Backup/restore reflects whichever local backend is currently
  authoritative, verified in both directions (LocalStorage sourcing
  with the marker absent; IndexedDB sourcing with it present, proven by
  deliberately diverging the two stores in a test).
- Backup format (version, section keys, structure) is unchanged —
  verified byte-for-byte across the migration.
- The pre-existing AN-014 contravariance defect in
  BackupSection.save's type (6 of the project's 7 known tsc errors) was
  left unfixed, per explicit scope — it is a type-level issue only, no
  runtime effect.

---

## Alternatives Considered

- Migrate all ten sections. Rejected: six were never part of the Step 6
  storage medium migration; touching them has no basis in the approved
  scope and would have expanded the file list well beyond what was
  authorized.
- Fix the AN-014 defect while touching these functions' signatures
  anyway. Rejected: explicitly out of scope; a separate, dedicated
  decision.

---

## Rejected Alternatives

Both above — rejected per stated reasons.

---

## Spec References

SYNC_ARCHITECTURE_SPEC.md §13 Step 6 sub-step 5 (resolver routing); Phase
20 audit note in backupService.ts (why RESTORE_POINTS/RECOVERY_BIN are
excluded from BACKUP_SECTIONS, unrelated to and unchanged by this
migration).

---

## Revisit Only If

The AN-014 type defect is taken up as its own approved fix, or a future
phase migrates any of the six remaining sections to a different storage
medium.

# AD-012

## Title

loadFailed safeguard in the four hydration hooks.

---

## Status

Approved

---

## Date

2026-08-02

---

## Context

The four hooks' hydration effects had no rejection handling on the load
path (only the save path was covered by BD-1). A rejected load left
`hydrated` false forever — App.jsx's gate has no timeout — stranding the
user on the loading spinner permanently, with an unhandled promise
rejection. Simply completing hydration on failure was considered, but a
naive version of that fix would persist the placeholder state (empty
array / DEFAULT_ACCOUNTS / mergeLists(null) / DEFAULT_SETTINGS) over the
user's real stored data on the very next persist-effect run — turning a
transient read error into permanent, silent data loss.

---

## Decision

Each hook's hydration effect gained `.catch()` (reports the failure via
reportLocalPersistenceFailure and sets a new loadFailed flag) and
`.finally()` (always sets hydrated, so the UI gate always releases). The
persist effect's guard was extended from `if (!hydrated) return;` to
`if (!hydrated || loadFailed) return;` — so a failed read completes
hydration (no permanent spinner) but permanently suppresses persistence
for that hook instance (no data loss), until the component remounts.

---

## Consequences

- Hydration always completes, verified directly (including under
  StrictMode's double-invoke).
- No scenario found, across refresh/login/logout/retry/StrictMode/
  marker-absent/marker-present, where the placeholder state overwrites
  real user data — verified with a forced read failure against real
  data in both stores, followed by a post-failure edit: neither store
  was altered.
- Disclosed consequence: a post-failure edit is accepted and displayed
  in the UI but silently lost on the next reload, since persistence
  stays suppressed. Judged the correct trade-off versus the alternative
  (destroying real data).
- Unreachable while the cutover marker is absent: LocalStorage's
  storageGet/storageSet swallow every error and cannot reject, so
  loadFailed can never become true in that configuration — verified,
  zero behavior change in the default state.

---

## Alternatives Considered

- Retry the load automatically on failure. Rejected: not requested,
  and would need its own backoff/retry-limit design; deferred rather
  than added speculatively.
- Leave hydrated false forever on failure (original bug). Rejected:
  permanent spinner, the defect being fixed.
- Complete hydration on failure without suppressing persistence.
  Rejected: proven to destroy real data in the first implementation
  attempt's design review.

---

## Rejected Alternatives

Both non-chosen behaviors above — rejected per stated reasons.

---

## Spec References

SYNC_ARCHITECTURE_SPEC.md §3.4 (failure must be surfaced, not silent);
Principle 1 (no silent data loss).

---

## Revisit Only If

A retry-on-failure UX is explicitly requested, or the local-persistence
notice gains a distinct "read failed" kind (AD-010's revisit condition)
that changes what loadFailed should trigger.

---

# AD-013

## Title

Per-callback failure isolation in the leader dispatch chain.

---

## Status

Approved

---

## Date

2026-08-02

---

## Context

enqueueLeaderCallback originally chained callbacks directly:
`dispatchChain = dispatchChain.then(() => callback())`. A rejecting
callback left dispatchChain permanently rejected; every later-registered
callback, chained onto the same promise, was silently skipped by
ordinary promise short-circuiting, and the rejection went unhandled. In
6g-2, the cutover registers before the Sync Engine — a failing cutover
callback would have silently prevented the engine's first cycle from
ever running.

---

## Decision

Each callback is wrapped in its own try/catch inside the chained
function: `dispatchChain = dispatchChain.then(async () => { try {
await callback() } catch (err) { console.error(...) } })`. The chain
itself can therefore only ever resolve, never reject, so no later
callback can be skipped by a failure. Logged via console.error, not
routed through reportLocalPersistenceFailure — a leader-callback failure
is not a local-persistence condition, and routing it there would
mislabel an unrelated error as a storage/quota problem.

---

## Consequences

- One failing callback can never prevent later callbacks from running —
  verified directly: 3 callbacks with the middle one throwing all ran,
  in order, exactly once each, with zero unhandled rejections.
- Combined with AD-007's epoch check (which runs first inside the same
  wrapper), a queued-but-cancelled callback is skipped before the
  try/catch is even reached, and a callback that both runs and fails is
  still isolated from its neighbors.
- A callback's own failure is only diagnostic-logged; the callback's
  owner remains responsible for any user-facing handling of its own
  failure (e.g. the cutover's own result object already carries failure
  detail via CutoverOutcome).

---

## Alternatives Considered

- Promise.allSettled over all callbacks instead of a serial chain.
  Rejected: would lose the registration-order guarantee (AD-005),
  which the cutover's must-settle-before-the-engine's-first-cycle
  requirement depends on.
- Let a failing callback's error propagate to the caller of
  startLeaderElection(). Rejected: leadership is granted asynchronously,
  often long after startLeaderElection() has already returned, so there
  is no caller left to propagate to.

---

## Rejected Alternatives

Both above — rejected per stated reasons.

---

## Spec References

None directly (implementation robustness); supports AD-005's ordering
guarantee and SYNC_ARCHITECTURE_SPEC.md §13 Step 6's requirement that a
failed cutover never destabilize anything else.

---

## Revisit Only If

A caller needs to be notified synchronously of a leader-callback
failure (no such need identified as of this phase).

# AD-014

## Title

Backtest results are unsynced local data, keyed by result ID, not a new synced table.

---

## Status

Approved

---

## Date

2026-08-03

---

## Context

Gap-analysis finding G-4 (Backtesting Foundation readiness review):
before any backtest result is persisted, the codebase needs a decided
answer for which of the two existing local-persistence classes it
belongs to.

Class A — synced business data (trades, accounts, lists, settings,
sync_cursors): accessed exclusively through the resolver
(services/localDatabase.ts), participates in sync, tombstones,
conflict detection (Tier 1/2), and the Step 6 atomic cutover.
SYNC_ARCHITECTURE_SPEC.md's four non-negotiable guarantees (no silent
loss/revert/local-overwrite/cloud-overwrite) apply in full.

Class B — unsynced local data (savedFilters, recoveryBin,
tradeReview settings): reads/writes services/storage.js directly,
bypassing the resolver entirely. SYNC_ARCHITECTURE_SPEC.md's own
stated scope already excludes this class from sync: "Does not cover
... Recovery Bin, Restore Points, Import/Export."

A backtest result is a deterministic simulation output (per the
accepted architecture blueprint: hypothetical, never persisted trade
data, never conflated with real L2 records) — regenerable at any time
from its inputs (the strategy definition and the trade history it ran
against). It carries no independent source-of-truth value the way a
manually-entered trade does: if lost, it is rerun, not un-recoverable.

---

## Decision

Backtest results are Class B: unsynced local data, read/written
directly via services/storage.js (or its IndexedDB equivalent, should
one be added later for this class specifically), never through
services/localDatabase.ts's resolver. They do NOT become a sixth
IndexedDB business store, do NOT carry SyncMetadata (§3.2), do NOT
participate in the Push/Pull Managers, Tier 1/2 conflict detection, or
the Step 6 cutover's copy/verify/completion-marker sequence.

Each backtest result is keyed by an independently generated result ID
(see calculations/idGenerator.ts's existing nextId(), already used for
FilterCondition/FilterGroup/SavedFilter/RestorePoint IDs — the same
"locally generated, never needs cross-device identity" pattern this
decision extends to backtest results) — not a syncId, and not a _tid
(the trade-specific identity `enrichTrades()` assigns).

---

## Consequences

- SYNC_ARCHITECTURE_SPEC.md ("Design frozen") is not reopened: adding
  a Class B data type requires no change to the spec, the resolver,
  the Sync Engine, or the Step 6 cutover — all of which are scoped to
  Class A only.
- IndexedDB stays at DATABASE_VERSION = 1 for this reason specifically:
  no new object store is required for backtest results, so this
  decision alone does not trigger the schema-bump risk tracked
  separately as gap-analysis finding G-3 (onIndexedDbBlocked has no
  subscriber). A future, independent decision to add local IndexedDB
  storage for backtest results would still need G-3 resolved first,
  same as any other future store addition would.
- A backtest result does not sync to a second device. A user switching
  devices does not see prior backtest runs — acceptable, since a
  result is reproducible on demand from its inputs, which (trades,
  strategy definitions) DO sync normally as Class A data.
- Backtest results are explicitly excluded from Backup & Restore
  (services/backupService.ts's BACKUP_SECTIONS) for the same reason
  Recovery Bin is excluded there today (documented in that file's own
  Phase 20 audit note) — regenerable derived output, not source data.
  A future phase MAY choose to add it for user convenience; that is a
  separate, smaller decision than this one and does not require
  revisiting this AD.

---

## Alternatives Considered

- Class A (synced business data, full resolver + sync integration).
  Rejected: drags a regenerable, hypothetical-by-definition value into
  the frozen sync spec's guarantees, conflict model, and cutover
  sequence — a heavy commitment for output whose whole purpose (per
  the accepted architecture blueprint) is to stay clearly separated
  from real trade records, not travel through the same identity and
  conflict machinery they do.
- A third, new persistence class specific to backtesting. Rejected as
  premature: Backtesting Foundation has not started, so no concrete
  requirement (result size, retention policy, query pattern) exists
  yet to justify a new class instead of reusing Class B, which already
  fits every currently-known property of a backtest result (local,
  regenerable, independently-keyed, no cross-device requirement).

---

## Spec References

SYNC_ARCHITECTURE_SPEC.md's explicit scope exclusion ("Does not cover
... Recovery Bin, Restore Points, Import/Export"); gap-analysis
findings G-3 and G-4 (Backtesting Foundation readiness review,
2026-08-03); the accepted architecture blueprint's Analytics <-
Backtesting <- AI layering (Backtesting output is hypothetical,
distinct from L2 real trade records).

---

## Revisit Only If

Backtest results need to sync across a user's own devices (a concrete
product requirement, not a convenience guess), or grow large/frequent
enough that direct LocalStorage access (Class B's current mechanism)
becomes impractical and a dedicated IndexedDB store is justified on
its own merits — at which point G-3 must be resolved first, since that
would be this project's first real schema bump.

- A new, separately-persisted BacktestInput/"strategy definition"

  14), and already has its own Class-B persisted form (SavedFilter) —

- Persisting the full equity curve for future charting convenience.
  Rejected: recomputable, and unbounded in size relative to matched-

Both above — rejected per stated reasons.

# AD-016

## Title

The global viewing lens is a pure calculations-layer function
(selectVisibleTrades); Backtest is exempt from it and always consumes
allTrades.

---

## Status

Approved

---

## Date

2026-08-04

---

## Context

Phase 14 built the Advanced Filters capability — a condition engine
(calculations/filterEngine.ts), a persistence hook
(hooks/useAdvancedFilters.ts) and a builder UI — but wired it into no
page. Its "Apply" action was literally an empty function in
SettingsModal. Meanwhile every page in the application read a single
derived array produced by useFilters.applyFilters, which understood
only two dimensions: account and market.

Phase 22 connected the two. That required deciding WHERE the composed
filtering rule lives, in what ORDER the filters compose, what "apply"
means with respect to the saved filter it came from, and whether the
Backtest page participates in the lens at all.

---

## Decision

1. THE RULE LIVES IN calculations/, NOT IN THE HOOK.
   calculations/visibleTrades.ts exports a pure function:

     selectVisibleTrades(trades, accFilter, mktFilter, activeGroup)

   It contains the account/market predicate moved verbatim out of
   useFilters.applyFilters, followed by the existing applyFilterGroup()
   when activeGroup is non-null. useFilters() retains only React state
   and delegates; it no longer decides what the application displays.
   The module imports only from calculations/ and types/ — never from
   hooks/, components/, pages/, services/ or sync/.

2. COMPOSITION ORDER IS FIXED: account → market → group.

3. SINGLE SOURCE OF TRUTH. selectVisibleTrades() is the only place the
   lens is computed. applyFilters() has exactly one call site in the
   entire source tree (App.jsx), and no page, component, hook or test
   re-implements the rule.

4. SNAPSHOT SEMANTICS. Applying a saved filter stores
   structuredClone(savedFilter.group) alongside its name and sourceId,
   as ActiveFilter. The active lens is a copy, not a live reference.

5. BACKTEST IS EXEMPT. pages/Backtest.tsx receives the UNFILTERED
   allTrades array and is the one page that does not read through the
   lens.

6. THE ACTIVE FILTER IS NOT PERSISTED. It is in-memory only and resets
   on reload, exactly like accFilter/mktFilter.

7. clearActiveFilter() CLEARS ONLY THE GROUP. Account and market
   filters survive it.

---

## Reason

1. This is business logic, and this codebase already has a settled
   convention for where business logic lives relative to React state:
   calculations/backtest.ts holds computeBacktestResult() while
   hooks/useBacktests.ts holds the state around it; the same split
   exists for analytics, drawdown, streaks and rolling. Placing the
   filtering rule in a hook would have made the single most
   consequential function in the application — the one deciding what
   every page displays — unreachable without rendering React, and would
   have put decision logic in the layer that is supposed to hold state.
   As a pure function it is tested directly, with no DOM and no test
   infrastructure change.

2. The three filters are a pure conjunction, so the result is
   order-independent and the order is a free choice. It is fixed
   anyway, for two reasons: determinism (one documented order means one
   reviewable behavior), and cost — account and market are single
   field comparisons that narrow cheaply, while the group evaluates
   every condition against every surviving trade.

3. Duplicating the rule is the specific failure this decision exists to
   prevent. The next phase most likely to want its own trade-selection
   logic is the AI layer, where "which trades should the model see" is
   a natural place to grow a second, subtly different filter. Playbook
   §3 forbids parallel implementations; making one function the only
   answer means a future consumer inherits filtering instead of
   reinventing it.

4. Without the clone, deleting a saved filter would mutate or
   invalidate what the user is currently looking at. Copying makes
   "apply" mean a point-in-time action rather than a live subscription,
   which is what the interaction visibly promises: the chip names a
   filter, it does not bind to one. sourceId records provenance without
   creating that binding.

5. A stored BacktestResult records its own filterGroup as the complete
   strategy definition (AD-015). If the global lens narrowed the input,
   a result would have been computed over a smaller set than its own
   filterGroup describes — silently, with nothing in the stored record
   indicating it. The result would no longer be self-describing, and
   two results run under different global filters would be
   incomparable while appearing comparable. This is the strongest
   correctness argument in the phase and is why the exemption is
   architectural rather than incidental.

6. The active filter is a viewing preference, not user data. Persisting
   it would require a new storage key, a Class A/B decision (AD-011,
   AD-014), and an answer for what happens when a persisted lens
   references a saved filter the user has since deleted. Matching the
   existing in-memory semantics of accFilter/mktFilter avoids all three
   and keeps the phase invisible to persistence.

7. The chip is attached to the strategy filter and names it. Clearing
   more than the control names would be a surprise, and the two filter
   surfaces are conceptually independent — the global bar answers
   "which account/market am I looking at", the chip answers "through
   which strategy".

---

## Tradeoff

1. AccountFilter ('all' | string) and MarketFilter ('all' | 'forex' |
   'futures') moved into the calculations layer with the predicate that
   consumes them. 'all' is a presentation convention meaning "this
   control is unset", so a pure business-logic module now carries a
   vocabulary that originated in the filter bar. A future change to how
   the UI represents "unset" would require editing calculations/.

2. Fixing the composition order means the cost characteristics are
   fixed too. A future filter type cheaper than the account check would
   not automatically run first.

3. selectVisibleTrades() returns the input array BY REFERENCE when
   accFilter and mktFilter are both 'all' and activeGroup is null. This
   is the original early-return behavior, preserved verbatim, and it
   means the function is not uniformly "always returns a new array".
   Callers must not mutate the result. Every filtering path does return
   a new array.

4. The clone means the active lens can drift from its source: a user
   who edits a saved filter sees no change in the active view until
   they re-apply it. This is deliberate but is a real discoverability
   cost.

5. The Backtest page is the one place in the application where the
   global filter visibly does nothing, which can read as a bug to a
   user who does not know the reason. The chip remains visible on that
   tab, which makes the discrepancy observable rather than hidden.

6. The active filter is lost on reload. A user with a habitual filter
   must re-apply it each session.

---

## Alternatives Considered

A. Keep the composed rule inside useFilters.ts as an exported helper.
   REJECTED: it puts decision logic in the state layer, contradicting
   the calculations/hooks split this codebase already follows, and
   leaves a pure function in a module whose other exports are all
   React-bound.

B. Give selectVisibleTrades a domain-level signature
   (accountId: string | null, market: 'forex' | 'futures' | null) with
   the hook translating 'all' to null.
   REJECTED: it adds a translation layer whose only purpose is
   vocabulary purity, creates a second encoding of "unset", and moves
   the predicate further from the verbatim form the phase required it
   to preserve. The sentinel has been stable since Phase 2B.

C. Store the active filter as a reference (sourceId only) and look the
   group up from savedFilters on each render.
   REJECTED: it makes the active view mutable by unrelated actions —
   deleting the saved filter would blank the application with no
   explanation, and editing it would silently change what the user is
   looking at.

D. Apply the global lens to the Backtest page for consistency.
   REJECTED: see Reason 5. Consistency is the wrong objective when it
   breaks the self-describing-result contract.

E. Give the Backtest page its own copy of the filtering logic so it can
   explicitly opt out.
   REJECTED: a second implementation of the rule, which is exactly what
   Decision 3 exists to prevent. Passing the unfiltered array is a
   one-line invariant with no duplicated logic.

F. Persist the active filter to LocalStorage.
   REJECTED for this phase: see Reason 6. Revisitable — see below.

---

## Consequences

- FilterGroup now has three uses rather than one: it is the strategy
  definition for backtesting (AD-015), the live viewing lens (this AD),
  and the natural scope object for any future feature that needs to
  reason about a subset of trades.
- Any future consumer wanting "the trades the user is looking at" calls
  selectVisibleTrades() or reads the derived array from App.jsx. There
  is no second answer.
- Pages became narrower-array consumers with no code change of their
  own. None was modified in Phase 22.
- Fixed-threshold analyses (pages/Insights.tsx in particular) can now
  receive arbitrarily small samples. No minimum-sample guard exists.
  Recorded as a known risk, not addressed.

---

## Spec References

AD-011 (SavedFilter is Class B, unsynced — the entity this lens
applies); AD-014 (Class B backtest results); AD-015 (FilterGroup is the
strategy definition for v1 backtesting — the decision this AD extends
from "definition of a backtest" to "definition of a view").

---

## Revisit Only If

- The account or market filter gains a third state (e.g. multi-select),
  at which point the 'all' sentinel stops being expressive and
  alternative B's translation layer becomes justified.
- Users report losing their filter across reloads often enough to
  justify the persistence decision deferred in Reason 6 — which would
  reopen the Class A/B question and require an answer for a persisted
  lens whose source filter no longer exists.
- A future phase has a concrete requirement for the Backtest page to
  respect the global lens, which would first have to resolve how a
  stored BacktestResult remains self-describing (AD-015).

# AD-017

## Title

Win-rate and outcome-percentage labels state their denominator. Both
win-rate definitions are retained, not consolidated; the Dashboard
outcome pie is a composition display and keeps its own labelling.

---

## Status

Approved

---

## Date

2026-08-05

---

## Context

Two different quantities were rendered under one word.

calculations/rolling.ts's summarizeTrades().wr divides by the decisive
trades only — green / (green + red). calculations/analytics.ts's
computeCoreAnalytics().winPct divides by every logged trade —
green / n. The divergence was deliberate and has been documented since
Phase 8 (analytics.ts, the winPct entry: "Deliberately different
denominator from the existing Win Rate KPI on the Dashboard page").

What was never documented, and never noticed, is that both reached the
user under the identical label "Win Rate". They diverge whenever any
trade is Breakeven or has a blank outcome — a structural property of
calcOutcome() (tradeCalc.ts), where _outcome is '' exactly when _r is
null and 'Breakeven' when |r| <= 0.2.

Two surfaces contradicted themselves within a single view:

- pages/Dashboard.tsx rendered the KPI "Win Rate" from summary.wr and,
  directly beneath it, an outcome pie whose legend divides by
  green + red + be — a third denominator.
- components/backtest/BacktestResultView.tsx rendered a KPI "Win Rate"
  from summary.wr and, in the table below it in the same card, a row
  "Win %" from core.winPct.

Measured on the live authenticated journal during Phase 23 runtime
verification — 74 trades: 16 Green, 45 Red, 10 Breakeven, 3 blank —
the same journal simultaneously displayed 26.2% (16/61), 23% (16/71),
22% (16/74) and 21.6% (16/74).

Phase 23 also found that neither analytics.ts nor rolling.ts had any
value-level test coverage, so no formula in either module was pinned
against an independently derived expectation.

---

## Decision

1. CANONICAL VOCABULARY. Every rendered metric derived from an outcome
   count names its denominator. Three canonical names exist:

     Win Rate (W/L only)
       = Green / (Green + Red)
       Excludes Breakeven AND blank/non-decisive outcomes.
       Source: summarizeTrades().wr (rolling.ts). Null when
       Green + Red is 0.

     Win Rate (all trades)
       = Green / total trades
       Source: computeCoreAnalytics().winPct (analytics.ts). Null when
       the trade set is empty.

     Win % / Loss % / Breakeven % (all trades)
       = each outcome count / total trades
       Source: winPct / lossPct / bePct (analytics.ts). These
       deliberately do NOT sum to 100% when blank-outcome trades
       exist, since such trades are counted in the denominator but
       match no outcome bucket.

2. LABEL MAP. The vocabulary is applied at exactly six sites, as text:

     Dashboard KPI                  -> "Win Rate (W/L only)"
     Insights StatBox               -> "Win Rate (all trades)"
     Backtest result KPI            -> "Win Rate (W/L only)"
     Backtest core table rows       -> "Win % (all trades)",
                                       "Loss % (all trades)",
                                       "Breakeven % (all trades)"
     Insights rule titles           -> "Strong All-Trade Win Rate",
                                       "Low All-Trade Win Rate (N%)"
     Insights good-rule body        -> "All-trade win rate N% ..."

3. BOTH DEFINITIONS ARE RETAINED. Neither formula is changed, removed,
   or redirected. calculations/analytics.ts and calculations/rolling.ts
   were not edited at all in Phase 23 — proven by SHA-256 comparison
   before and after, including across two mutation spot-checks.

4. THE DASHBOARD OUTCOME PIE IS EXEMPT. Its legend keeps the form
   "Green N (P%)" over the denominator green + red + be, unchanged.
   It sits in a card already titled "Win / Loss / BE" and answers
   "what was the composition of my classified trades", not "what is my
   win rate".

5. THE DIVERGENCE IS ENFORCED BY TEST, NOT BY CONVENTION.
   calculations/analytics.test.ts asserts that winPct and
   summarizeTrades().wr differ on a set containing Breakeven and blank
   outcomes, and that they agree when every trade is decisive. Both
   values are pinned exactly.

---

## Reason

1. A label is a claim about what a number means. Two numbers under one
   word is not a naming inconvenience — on the Dashboard and in the
   Backtest result card a user could read 26.2% and 22% within one
   screen and have no way to learn that the difference is the
   denominator rather than an error. Naming the denominator is the
   smallest change that makes each number self-describing.

2. Both definitions are legitimate and answer different questions.
   "Of the trades that resolved decisively, how many won" is the right
   denominator for expectancy, Kelly and risk-of-ruin, which are all
   computed over closed trades. "Of everything I logged, how many won"
   is the right denominator for judging a journal including its
   incomplete entries. Consolidating would have silently changed one
   page's long-standing output and destroyed information, and it is a
   formula change — forbidden by Playbook §4 without explicit approval.

3. "(W/L only)" rather than "(excl. BE)". The decisive-trade
   denominator excludes TWO categories, not one: Breakeven trades and
   blank/non-decisive outcomes (_r === null). "(excl. BE)" was
   proposed, reviewed and rejected during RFC finalisation precisely
   because it names only one of the two exclusions and would have
   substituted a subtler mislabel for the original one.

4. The pie is a different kind of object. A composition chart's slices
   are shares of what was classified; forcing win-rate vocabulary onto
   it would imply it is a fourth win-rate reading rather than a
   breakdown, which is the opposite of the phase's goal.

5. Tests before vocabulary. A naming decision about a metric layer that
   nothing verifies is a decision about a moving target. Phase 23 added
   value-level characterization tests for both modules first, with every
   expectation hand-derived from the documented FORMULA blocks, so the
   vocabulary now describes behavior that is pinned rather than assumed.

---

## Tradeoff

Labels are longer, and two names now exist for what users colloquially
call one thing, which is a small ongoing cost in UI density and in
explaining the product. Accepted because the alternative is a number
that cannot be interpreted without reading source.

Retaining both formulas also means the codebase permanently carries two
win-rate definitions. That is a real maintenance surface: any future
metric or AI narration layer must choose one deliberately. AD-017 exists
so that choice is made against a written vocabulary instead of by
picking whichever function is nearest.

A residual, deliberately untouched inconsistency remains: the same
all-trades quantity renders as 22% on Insights (Math.round) and 21.6%
in the Backtest table (fr.pct, toFixed(1)). This is display PRECISION,
not a difference of formula or denominator. It predates Phase 23 and was
left unchanged, since altering it is a rendering change beyond a label.

---

## Alternatives Considered

A. Consolidate onto one win-rate definition and delete the other.
   REJECTED: a formula change (Playbook §4), silently altering a
   page's output that has been stable since Phase 6/8, and destroying
   the distinction that expectancy/Kelly/risk-of-ruin depend on.

B. Change only the labels that collide, leaving the Insights rule
   titles ("Strong Win Rate", "Low Win Rate (N%)") ambiguous.
   REJECTED during RFC finalisation: the rule cards restate the same
   metric in prose directly beneath the StatBox, so leaving them would
   have preserved the exact ambiguity the phase exists to remove.

C. Relabel the Dashboard outcome pie legend as well.
   REJECTED: see Reason 4. Recorded as RFC open question OQ-2 and
   explicitly approved as "leave unchanged".

D. Use "(excl. BE)" for the decisive-trade denominator.
   REJECTED: see Reason 3 — it names only one of the two exclusions.

E. Add a tooltip or help icon explaining each denominator instead of
   changing labels.
   REJECTED: introduces a new interaction and component surface for
   what a longer label solves, and hides the disambiguation behind a
   hover the user must first suspect they need.

F. Unify the display precision of the all-trades percentage across
   Insights and the Backtest table.
   REJECTED for this phase: out of the approved text-only scope. See
   Tradeoff and Revisit Only If.

---

## Consequences

- Every rendered outcome-derived percentage in the application now
  states its denominator, except the outcome pie, which is exempt by
  decision 4.
- calculations/analytics.ts and calculations/rolling.ts gained their
  first automated coverage: 53 new assertions across two test files,
  taking the suite from 61 to 114 tests over 6 to 8 files.
- The divergence between the two definitions is now a tested property.
  A future change that collapses either formula into the other fails
  the suite: verified by mutation, in both directions.
- A future AI or narration layer that reports "win rate" must pick a
  canonical name from decision 1 and say which it means. There is no
  longer an undocumented default.
- Class-B functions in rolling.ts (getTradeFrequency, getRollingStats,
  getStandardRollingWindows, and getWeekKey's Monday-start semantics)
  remain untested by deliberate decision — they carry no
  Formula/Source/Assumptions block, so a test would manufacture a
  contract rather than verify one.

---

## Spec References

AD-015 (BacktestResult composes CoreAnalytics directly — the reason 26
of the 34 core fields are reachable only through the Backtest tab, and
why the Backtest card is where the two definitions met in one view);
AD-016 (the global lens, which made the visible trade set
user-narrowable and so raised the cost of an ambiguous metric).

---

## Revisit Only If

- A future phase has a concrete requirement to report a single
  authoritative win rate — for example an AI narration layer or an
  exported report — which would reopen alternative A and require an
  explicit decision about which definition is canonical for that
  consumer, rather than a silent choice.
- The display-precision inconsistency recorded under Tradeoff (22% vs
  21.6%) is judged worth correcting, which is a rendering change and
  needs its own approval (alternative F).
- The outcome pie is redesigned or moved out of its "Win / Loss / BE"
  card, at which point decision 4's justification no longer holds.
- A Class-B function in rolling.ts gains a documented contract, at
  which point it becomes eligible for the coverage this phase
  deliberately withheld.

# AD-018

## Title

New BacktestResults persist a raw cumulative equity path; legacy
results remain unmigrated and visibly reconstructed.

---

## Status

Approved

---

## Date

2026-08-05

---

## Context

AD-015 clause 2 deliberately excluded the full equity curve from
BacktestResult because it was considered recomputable from
matchedTradeIds plus startingCapital. That was valid for a regenerable
result, but it is not valid for an immutable historical snapshot.
Opening a saved result resolved matchedTradeIds against current journal
trades and rebuilt its equity curve, Ending Equity, and comparison
return series from current _netPL values. Editing or deleting a matched
trade could therefore change those analytical outputs while the stored
summary, drawdown, streak, and core metrics remained fixed.

The original path of a result created before the path was persisted is
not recoverable. Reconstructing it from current trades and writing that
reconstruction back would fabricate history rather than migrate it.

---

## Decision

1. Every new BacktestResult persists equityPath: the raw, unrounded
   cumulative equity after each matched trade, in matched order.
   startingCapital is the implicit point zero. The array has exactly
   tradeCount entries; [] means zero matched trades. A null _netPL
   contribution repeats the preceding cumulative value, matching the
   calculation contract used when the result is created.
2. Presence of equityPath is the sole discriminator for a new frozen
   result. For such a result, the Equity Curve, Ending Equity, and both
   sides of a comparison return chart derive from equityPath and
   startingCapital, not from current journal trades.
3. Absence of equityPath identifies a legacy result. Legacy records are
   not migrated, backfilled, or rewritten. Their Equity Curve and
   Ending Equity may continue to be reconstructed from currently
   resolvable journal trades, but the result view must label those two
   outputs as reconstructed current-data values rather than part of the
   historical snapshot. A comparison must label each legacy series on
   its own side. Stored legacy metrics remain unchanged.
4. AD-015 clause 2 only is superseded. Its prohibition on a persisted
   equity curve and its recomputation requirement no longer govern new
   BacktestResults. AD-015 clauses 1 and 3 remain approved and
   unchanged. AD-014 is not amended: BacktestResults remain capped,
   unsynced Class-B LocalStorage data outside the resolver, IndexedDB,
   Sync Engine, cutover, and Backup & Restore.

---

## Reason

The saved-result card must not combine frozen metrics with a curve and
endpoint that silently move when source trades change. Persisting the
already-computed cumulative path is the smallest sufficient additive
snapshot: one numeric array serves the absolute equity chart, Ending
Equity, and percentage-return comparison without persisting full
trades or chart presentation objects. Raw values preserve the existing
unrounded comparison precision; display rounding remains a rendering
concern.

Keeping equityPath optional provides backward compatibility without a
version field or a storage migration. Explicit legacy notices preserve
the utility of old results without claiming that an unrecoverable path
is historical.

---

## Consequences

- New saved results remain analytically and visually stable after
  matched trades are edited or deleted and after a JSON persistence
  round-trip.
- Storage grows by one number per matched trade. The existing cap of 50
  results still applies.
- Legacy results remain readable and retain their stored metrics, but
  their reconstructed curve, Ending Equity, and comparison series are
  permanently qualified. This limitation cannot be removed for
  already-saved records because their original paths were never stored.
- No DATABASE_VERSION bump, migration, sync change, resolver change,
  IndexedDB change, cutover change, backup expansion, or new dependency
  is introduced.
- matchedTradeIds and unresolved-count disclosure remain for
  traceability; they are not the analytical source for a new result's
  frozen equity outputs.

---

## Alternatives Considered

- Persist full matched trades. Rejected: duplicates journal records and
  greatly exceeds the information needed by the affected outputs.
- Persist rounded chart points or separate absolute and percentage
  presentation series. Rejected: duplicates derivations, bakes UI shape
  into storage, and can lose comparison precision.
- Persist per-trade net P/L instead of cumulative equity. Sufficient,
  but rejected because the cumulative sequence is already computed at
  run time and can be consumed directly without render-time
  accumulation.
- Migrate or lazily backfill legacy records. Rejected: current trades
  cannot authenticate or reproduce the original historical path, so
  backfill would freeze a reconstruction as if it were history.
- Suppress legacy curves and Ending Equity entirely. Rejected: clear,
  local notices preserve useful current-data reconstruction without
  misrepresentation.

---

## Spec References

AD-014 (BacktestResults remain unsynced Class-B local data); AD-015
(clauses 1 and 3 remain in force; clause 2 is superseded only by this
decision); the Phase 26 Immutable Backtest Equity Snapshots RFC.

---

## Revisit Only If

- BacktestResults gain a concrete cross-device sync or backup
  requirement, which would reopen AD-014 independently of this equity
  snapshot decision.
- A future analytical output requires historical trade attributes not
  derivable from the stored result and equityPath; that output needs its
  own snapshot contract rather than silently reading mutable trades.

# AD-019

## Title

Local Durability and Backup Integrity

---

## Status

Approved

---

## Date

2026-08-06

---

## Context

AD-014 excluded saved Backtest Results from Backup & Restore because it
classified them as regenerable derived output. AD-018 later made every
new result an immutable historical snapshot by persisting its raw equity
path; that history cannot be faithfully recreated after its source trades
change. The Recovery Bin exclusion was likewise based on the now-obsolete
premise that the bin was always empty. The application now soft-deletes
real trade snapshots into it before removing active trades.

Restore validated only its outer envelope, then wrote present sections
sequentially. Direct LocalStorage helpers deliberately swallow failures,
so restore could report success without evidence that a write persisted.
Saved Backtest creation also silently evicted the oldest result when a
51st result was added, contradicting the historical-record contract.

---

## Decision

1. Saved Backtest Results belong to Backup & Restore because AD-018 made
   new results immutable historical records. Recovery Bin belongs because
   it contains real recoverable records.
2. Backtest Results remain LocalStorage-only, Class B, unsynced, and
   outside the resolver, IndexedDB, Sync Engine, and cutover.
3. Backup format v2 contains 12 centralized sections. Restore accepts
   supported versions 1 and 2 only.
4. Restore validates the supported envelope and every present known
   section before the first write. Every known section is optional; a
   missing section leaves live state untouched. Unknown sections are
   ignored, while additive fields on otherwise-valid records are
   preserved.
5. Every non-null restore write is reloaded through its registered load
   path and compared with the once-revived expected semantic state.
   Detected persistence failure is surfaced, aborts later writes, and
   cannot produce a success result.
6. Restore is sequential. Cross-section rollback and transactional
   atomicity are not guaranteed; earlier verified sections may remain
   changed after a later failure.
7. Saved Backtest creation at count 50 or greater is blocked before
   result computation. Existing results, including restored collections
   above 50, are preserved without eviction, slicing, trimming, or
   migration.
8. Restore Points inherit Recovery Bin and Backtest Results through the
   centralized `buildBackup()`. Restore Points themselves remain excluded
   to prevent recursive snapshots and stale-point-list replacement. Sync
   cursors also remain excluded.
9. The global `storageSet` contract remains unchanged. Checked persistence
   is confined to the backup/restore durability boundary.

---

## Supersession

- AD-014 is superseded only where it excludes Backtest Results from
  Backup & Restore on the former regenerable-results premise. Its Class B,
  local-only, unsynced, non-resolver storage classification remains in
  force.
- AD-018 clause 4 is superseded only where it continues the Backtest
  Results Backup & Restore exclusion. Its immutable equity snapshot and
  legacy-result contracts remain unchanged.
- AD-015 is superseded only where its saved-result cap policy requires
  evicting the oldest result. Its strategy-definition and BacktestResult
  composition decisions remain unchanged.

AD-014, AD-015, and AD-018 remain preserved as historical records.

---

## Reason

Data presented as saved, recoverable, or historical must not be omitted
from a complete backup, silently discarded at a retention boundary, or
reported as restored without evidence of persistence. Centralized section
validation and registered-path read-back verification close those gaps
without redesigning LocalStorage or widening Backtest Results into sync.

---

## Tradeoff

Restore now rejects structurally unsafe files that older code could pass
to storage helpers. Restore Points consume more LocalStorage because they
include two additional datasets. Sequential save/reload verification can
detect and report failure but cannot undo an earlier successful section.

---

## Alternatives Considered

- Change `storageSet` globally to throw or return a result. Rejected: it
  changes the persistence contract for unrelated workflows and creates a
  substantially larger regression surface.
- Add Backup coverage without validation and read-back verification.
  Rejected: omission would be fixed while false-success and malformed
  replacement risks remained.
- Add transactional rollback. Rejected: LocalStorage and IndexedDB do not
  share a transaction, and a rollback engine would exceed this bounded
  durability phase.
- Trim restored Backtest collections to 50. Rejected: it would destroy
  historical records during restore.
- Enforce exact schemas. Rejected: it would reject compatible additive
  historical fields and freeze unrelated domain models at the backup
  boundary.

---

## Consequences

- New backups and Restore Points cover Recovery Bin and saved Backtest
  Results; version-1 backups remain restorable.
- Malformed present known sections reject the complete restore before any
  write. Missing sections never clear live state.
- A detected failed or dropped write cannot be reported as successful.
- Result #51 cannot silently remove an existing historical result.
- No migration, storage-key change, IndexedDB change, resolver change,
  sync change, cutover change, or dependency is introduced.

---

## Spec References

AD-014 (Backtest Results Class B classification and historical backup
exclusion); AD-015 (BacktestResult composition and former eviction cap);
AD-018 (immutable Backtest equity snapshots); the Phase 27 Local
Durability & Backup Integrity FINAL RFC.

---

## Revisit Only If

- A concrete product requirement adds cross-device Backtest sync, which
  would reopen AD-014's Class B decision independently of backup.
- Restore requires true cross-section rollback, which would require a
  separately approved transaction/rollback architecture.
- Restore Point growth becomes impractical under measured browser quota
  pressure, requiring an independently approved retention or storage
  policy.

---

# AD-020

## Title

Authenticated Local Ownership and Per-User Storage Isolation

---

## Status

Approved

---

## Date

2026-08-07

---

## Context

Authentication previously identified the remote account while normal
browser-local journal persistence continued to use shared global LocalStorage
keys. Two authenticated users in one browser profile could therefore inherit,
read, or overwrite the same local journal. Selecting storage through mutable
global current-user state would also permit stale asynchronous work to write
into a later session's namespace.

Existing installations may contain physically present data under historical
global keys, including default-looking values, malformed JSON, and a global
Sync cursor. Automatically assigning that data to the next user would turn
login order into an ownership decision. Existing global IndexedDB state has
the same migration ambiguity and must not be opened or created incidentally.

Portable backup files are different: they represent an explicit transfer of
logical journal data. Binding them to an exporting UUID or exposing physical
namespace keys would unnecessarily prevent intentional transfer.

---

## Decision

1. Authenticated browser-local persistence is isolated by exact authenticated
   user ID. Every key in the frozen 14-key inventory is addressed as
   `fxj:user:v1:<encodeURIComponent(exactUserId)>:<logicalKey>`. The validated
   UUID's case and bytes are preserved rather than normalized.
2. Authenticated storage routing is captured by the session and provided
   through a context-bound facade/database. Normal authenticated persistence
   must use that captured scope, never mutable global current-user state. The
   ownership/storage boundary is keyed by exact authenticated session ID and
   completes before the journal application mounts.
3. Existing global LocalStorage data uses explicit ownership, not automatic
   adoption. Physical raw presence under a recognized key is authoritative;
   `[]`, `{}`, `null`, and default-looking values are present data. Malformed
   recognized JSON is quarantined.
4. Legacy authority has five states: `legacy_absent`,
   `legacy_detected_unclaimed`, `claim_in_progress`,
   `claim_failed_retryable`, and `claim_verified`. Claim and decline are
   explicit actions. Claim reserves one exact owner, and only that owner may
   retry or overwrite partial destination residue.
5. Ownership transitions are serialized by the Web Lock
   `trading-journal-ai:legacy-claim:v1`. No LocalStorage lease or polyfill
   fallback is acceptable; unsupported locking fails closed.
6. Claim authority requires a canonical SHA-256 source digest, destination
   copy, destination read-back, preserved-source re-digest, completed-copy
   verification, and final registry verification. `claim_verified` is written
   and read back only after all prior steps succeed. Partial copied residue is
   not authority.
7. The global legacy source remains preserved after claim. Preservation
   supports audit and retry; it does not grant another user authority.
8. The legacy global Sync cursor participates in detection, snapshot, and
   digest. It remains preserved globally but is never transferred into an
   authenticated namespace. A newly scoped Sync cursor starts absent.
9. Existing global `trading-journal-ai` IndexedDB state is examined only by
   the frozen read-only preflight. The preflight must not create an absent
   database. Marker-present, unreadable, or unsafe enumeration/read conditions
   fail closed pending a separately approved migration.
10. Dormant global persistence accessors are compatibility surface, not
    authority for authenticated business writes. Authenticated startup must
    not silently reactivate the historical global Sync/Cutover path; an
    incompatible enabled condition fails closed.
11. Portable Backup/Restore remains user-ID agnostic. It carries logical
    journal data, not physical namespace keys or owner UUID requirements, and
    restore targets only the current authenticated scope. Restore Points remain
    user-scoped and excluded; Sync cursors remain excluded.
12. This decision does not establish per-user IndexedDB, full Sync
    reactivation, full Cutover reactivation, or general authentication-
    transition cancellation/generation. Each requires separate approval.

---

## Reason

Authentication is not local-data isolation unless every persistence operation
has an immutable owner for its lifetime. Exact-ID namespacing separates users,
and captured scope prevents authentication transitions from retargeting work.

Legacy ownership cannot be inferred safely from truthiness, default
equivalence, or login order. Explicit choice plus serialized, digest-verified
copy establishes authority without deleting the source or treating incomplete
copy residue as success. Cursor exclusion prevents inheritance of remote
progress belonging to an unknown historical identity.

Fail-closed IndexedDB inspection extends the same rule across storage
technologies. Backup stays portable because explicit import and logical payload
form a separate boundary from ambient browser ownership.

---

## Tradeoff

Successful claim duplicates data because the global source is preserved. An
explicit wrong-user reservation can strand ownership pending future handling.
Web Locks support is mandatory, and ambiguous global IndexedDB blocks local use
rather than risking misassignment.

Captured scope does not cancel every asynchronous operation created before an
authentication transition. General cancellation/generation remains deferred.

---

## Alternatives Considered

- Normalize or lowercase user IDs. Rejected: authenticated identity bytes are
  the ownership key; normalization introduces aliasing.
- Route through mutable global current-user state. Rejected: delayed work can
  be retargeted after an authentication transition.
- Assign legacy data to the first user. Rejected: login order is not ownership
  evidence.
- Ignore falsey or default legacy values. Rejected: physical presence remains
  user-owned state and migration eligibility.
- Move legacy data and delete its source. Rejected: deletion removes audit and
  retry evidence.
- Use a LocalStorage lease without Web Locks. Rejected: it creates a second,
  weaker ownership protocol.
- Transfer the legacy Sync cursor. Rejected: its authenticated owner is
  unknown.
- Open or create IndexedDB during preflight. Rejected: creation mutates absent
  state and opening ambiguous global state can trigger unsafe migration.
- Bind backups to the exporting UUID. Rejected: explicit portability is
  intentional and destination ownership is supplied by authentication.

---

## Consequences

- Authenticated users in one browser profile have distinct physical keys and
  context-bound persistence routing.
- The journal mounts only after ownership and IndexedDB safety are established.
- Legacy claim is explicit, serialized, source-preserving, and verified;
  decline creates an independent scope without authority.
- Malformed data, unsupported locking, and unsafe IndexedDB fail closed.
- Scoped Sync starts without a cursor, and authenticated startup cannot
  silently use the global Sync/Cutover path.
- Portable Backup/Restore may intentionally move logical journal data between
  users; Restore Points remain isolated to their authenticated scope.
- Global compatibility accessors may remain dormant but do not authorize a
  scoped-persistence bypass.
- Future phases may extend or supersede AD-020 only through a later explicit
  decision; they must not silently violate it.

---

## Spec References

Phase 32A Final RFC and amendments; Phase 32B implementation authorization and
bounded runtime completion pass; AD-004 through AD-013 (resolver, Sync, and
cutover architecture); AD-019 (portable Backup/Restore durability contract).

---

## Revisit Only If

- Per-user IndexedDB receives an approved physical database and migration
  contract.
- Sync or Cutover is reactivated for authenticated scoped persistence.
- General authentication-transition cancellation/generation is designed.
- Safe administrative recovery for wrong-user reservation is required.
- Portable backup identity or authorization requirements change.

# AD-021

## Title

NinjaTrader Futures Import: Flat-to-Flat Journal Trade Identity and Additive
Leg Foundation

---

## Status

Approved

---

## Date

2026-08-10

---

## Context

NinjaTrader's Trade Performance `Trades` export is not a list of logical
journal trades. Measured against a real export, 19 executions correspond to 9
logical flat-to-flat position episodes, and one of those episodes — a Qty-6
Short — appears in the `Trades` grid as two separate rows because the entry
filled in two parts:

    Sell 2 @ 29634.25  ->  Sell 4 @ 29634.75  ->  Buy 6 @ 29668.00  ->  flat

Both entry fills carry the same timestamp, so timestamps cannot order or
identify them. The user confirmed the trading intent: a single limit order that
partially filled, was left as price moved away, and completed on the return.

Per-row cost in the `Trades` export is also unreliable for a split episode. For
the rows above, the fee columns allocate `4.36 / 7.04` while the reported
profit implies `3.80 / 7.60`; only the episode total, `11.40`, is consistent.

The two exports are individually insufficient. The Executions export carries
structure, per-execution identity, and account, but only a partial `Commission`
figure — roughly 41% of true cost in every measured episode. The Trades export
carries the complete cost columns but the wrong granularity. The Orders export
carries order identity, but the Executions export leaves `Order ID` blank, so
the two cannot be joined and order identity is unavailable at import time.

Existing calculations are keyed on root symbols in the pip table. The source
supplies dated contracts such as `MNQ SEP26`, which is absent from that table:
validation rejects it, and market detection would silently classify it as
Forex at point value 1 instead of futures at 2.

---

## Decision

1. **Journal Trade identity is the flat-to-flat episode.** A trade opens when
   the signed position for a given source account and source instrument leaves
   zero and closes when it returns to zero. Partial fills, intentional
   scale-ins, and partial exits all belong to that same trade while the
   position is non-zero. Execution ID is provenance and ordering only, never
   logical-trade identity.
2. **The Executions CSV reconstructs episode structure and legs.** Executions
   are partitioned by source account plus full source instrument and ordered by
   execution ID using arbitrary-precision comparison, never JavaScript numbers.
   NinjaTrader's `E/X` column is cross-checked against the computed side and
   any disagreement aborts.
3. **The Trades CSV reconciles complete cost.** Trades rows are consumed in
   order by quantity conservation within the same partition. Timestamp equality
   is never used as identity.
4. **The Orders export is discovery evidence only** and is not a runtime import
   input.
5. **Pair reconciliation is fail-closed and all-or-nothing.** After consumption,
   total quantity, direction, scaled-integer sums of entry and exit price times
   quantity, and the Executions-versus-Trades commission subtotal in integer
   cents must all agree exactly. No floating tolerance is used. Any mismatch,
   or any unconsumed Trades row, aborts the entire import before persistence.
6. **Legs are optional and additive.** `legs`, `sourceInstrument`,
   `sourcePlatform`, and `sourceAccountId` are optional fields on the trade
   shape. Historical and manual trades carry none of them, remain valid, and
   are never migrated to populate empty values.
7. **Aggregate fields remain the compatibility surface.** Every existing
   calculation continues to read the aggregates only; legs are additive detail
   that no v1.2 calculation consumes.
8. **Root symbol and source contract identity are stored separately.** `symbol`
   holds the supported root used by the pip table; `sourceInstrument` holds the
   original dated contract verbatim.
9. **Composite source provenance supports idempotency**, conceptually
   `sourcePlatform + sourceAccountId + sourceInstrument + sourceExecutionId`.
   An episode whose executions are all already present is skipped, all-new is
   imported, and partial overlap aborts.

---

## Aggregate Semantics

- `entryPrice` — quantity-weighted average of entry-side legs.
- `exitPrice` — quantity-weighted average of exit-side legs.
- `positionSize` — total entry-side quantity.
- `commission` — the complete all-in episode cost, summed across every
  reconciled Trades row as
  `Commission + Clearing Fee + Exchange Fee + IP Fee + NFA Fee`.
- P/L, R, points, and outcome remain derived through the existing calculation
  path. NinjaTrader's `Profit` column is never read and never stored as
  authoritative P/L; it already includes fees and would double-count.

Weighted-average aggregation is P/L-preserving rather than approximate.
Flat-to-flat guarantees that total entry quantity equals total exit quantity,
and weighted average times that quantity is by definition the sum of price
times quantity, so the aggregate reproduces the leg-wise gross exactly.

`positionSize` is total entry-side quantity and is therefore **not necessarily
peak simultaneous exposure** when an episode scales out and back in before
going flat. Every consumer of the field multiplies it or displays it; none
interprets it as peak exposure.

---

## Safety Boundaries

Broker import fails closed, before anything is persisted, for:

- reconciliation mismatch on quantity, direction, price sums, or commission;
- an incomplete position episode, whether still open at the end of the range or
  beginning with an exit that implies a pre-existing position;
- reversal through zero within one execution;
- an episode whose first entry date differs from its final exit date
  (overnight);
- an unsupported NinjaTrader root outside `NQ`, `ES`, `MNQ`, `MES`;
- an unmapped source account;
- partial execution-ID overlap against already-imported data.

There is no partial success. Attaching complete costs to the wrong logical
trade is the specific failure this contract exists to prevent.

---

## Time Semantics

NinjaTrader source timestamps carry no timezone marker. They are treated as
already New York-local wall-clock time. No UTC offset and no DST arithmetic are
invented. The import UI states the assumption and requires explicit
acknowledgement before import is enabled.

Aggregate `entryTime` and `exitTime` are truncated — never rounded — to `HH:mm`
so the existing canonical-time validation is satisfied without relaxation.
Legs retain full `HH:mm:ss`.

---

## Reason

Order ID was the intuitive grouping key and is unusable: the Executions export
leaves it blank, so it cannot be joined to the Orders export. Timestamps
collide within a real episode. Position-evolution from signed quantities is the
only key the data actually supports, and it also matches the user's own
definition of a trade, which is what the journal is for.

Legs are required rather than cosmetic. The weighted-average entry for the
measured split episode is `29634.5833...`, a price off the instrument's tick
grid that was never traded and cannot be reversed into its constituent fills.
Collapsing to that average at import would destroy the detail permanently and
force a migration when scale editing is added.

Keeping the aggregates authoritative is what makes the change safe: no
calculation, analytic, chart, export, or backup path had to change.

---

## Tradeoff

Requiring two files is more friction than one, and it is accepted because
neither export alone can produce a correct trade: one lacks complete cost, the
other lacks correct granularity. The alternative — importing Executions only
and understating trading cost by roughly 59% — was rejected as silently wrong.

Restricting broker import to four roots is narrower than the pip table
supports. It is accepted because only MNQ and NQ appear in the evidence, and
breadth without evidence is how silent misclassification enters.

---

## Alternatives Considered

- **Import the `Trades` export directly.** Rejected: one logical trade can span
  several rows, and per-row fee allocation is provably inconsistent for exactly
  those rows.
- **Group executions by Order ID.** Rejected: the field is blank in the
  Executions export, so the join does not exist.
- **Group by matching timestamps and prices.** Rejected: the real episode has
  two entry fills sharing one timestamp, so the signal is coincidental and the
  rule would be fragile.
- **Store the dated contract in `symbol`.** Rejected: it is absent from the pip
  table, so validation rejects it and market detection would classify it as
  Forex at point value 1 rather than futures at 2.
- **Collapse to weighted averages without legs.** Rejected: irreversible
  information loss and a forced later migration.
- **Add a second fee field to mirror NinjaTrader's labels.** Rejected: the
  single existing Commission field, populated with the complete cost, satisfies
  the product requirement without widening the schema.
- **Bump the backup format version.** Rejected: additive optional fields
  already survive the existing format, and bumping would stop v1.1 from reading
  v1.2 backups for no gain.

---

## Consequences

- The trade shape gains four optional fields. `syncMappers.ts` had to be
  updated because its field map is declared `satisfies Record<keyof
  RawTradeContent, string>` and fails typecheck otherwise; `legs` required
  JSON-aware handling rather than the existing string sentinel, which would
  have stringified the array.
- Backup format stays at version 2. Legs round-trip, and a v1.1-shaped backup
  still restores.
- Validation of the new fields is lenient and runs only when a field is
  present, because backup restore validates every active trade and aborts the
  whole restore on the first error. Historical trades must produce zero errors.
- Broker-imported trades carry no stop loss, because the source has none, so
  they have no R and no outcome classification. This is the existing documented
  behaviour for non-decisive trades (see AD-017); v1.2 increases how often it
  occurs rather than changing it. Nothing is invented to fill the gap.
- The NinjaTrader path deliberately bypasses `smartAutoMap`, `convertRow`, and
  `detectDuplicate`, so the generic import path cannot regress through it.

---

## Spec References

v1.2 Final RFC, targeted amendment, and implementation preflight; v1.2
implementation, runtime-verification, and scoped P2 repair authorizations;
AD-017 (win-rate and outcome denominators); AD-019 (portable Backup/Restore
durability contract); AD-020 (authenticated local ownership and per-user
storage isolation).

---

## Revisit Only If

- Manual Scale In / Scale Out editing is approved, at which point the leg model
  becomes read-write rather than import-only.
- Overnight episodes or reversal through zero require support.
- A second broker or platform source is approved, at which point the
  source-specific adapter boundary should be re-examined before any
  generalization.
- NinjaTrader changes its export columns, adds `Order ID` to Executions, or
  exposes the full fee set there, which would collapse the two-file contract to
  one.
- Additional NinjaTrader Futures roots are approved for broker import.
- Aggregate `positionSize` semantics need to distinguish transacted quantity
  from peak simultaneous exposure.
