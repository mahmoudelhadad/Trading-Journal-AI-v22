## Summary

v1.7 delivers B2a: the first user-facing historical Replay core. A separate
Replay tab reads the provider-neutral local historical data introduced in v1.6
and renders one deterministic Lightweight Charts candlestick pane. Replay is
driven by a canonical UTC cursor, reveals only closed bars, derives higher
timeframes only from revealed 1-minute observations, and remains independent of
the existing Backtest feature.

## Delivered scope

- Separate Replay tab with one Lightweight Charts 5.2.1 candlestick pane.
- Local NQ and ES series selection and NinjaTrader historical import UI.
- Play, Pause, Step Forward and exact UTC Go To controls.
- Speeds: 1×, 2×, 5×, 10×, 30×, 60× and 300×.
- Timeframes: 1m, 5m, 15m and 1h.
- Deterministic UTC cursor with America/New_York display formatting, explicit
  UTC offset and ISO-UTC identity.
- DST-safe repeated-hour handling without shifting chart timestamps.
- No-look-ahead reveal, no partial 1-minute candle and no future autoscale or
  HTF contamination.
- HTF OHLCV folding from revealed 1-minute bars only; market gaps stay absent.
- Windowed initial loading, buffer-only forward prefetch, authoritative
  coverage extension and cursor-driven retention.
- IndexedDB reader pruning to the canonical requested UTC-day range.
- Same-App import barrier and stale asynchronous authority protection.
- StrictMode-safe App-lifetime runtime ownership with one frame loop and one
  visibility listener.
- Page Visibility suspension and automatic valid-intent resumption from a fresh
  monotonic anchor, with no hidden-duration catch-up.
- Explicit `read_failed`, `series_unavailable` and successful-empty-window
  semantics.
- Local production and `/Trading-Journal-AI-v22/` base-path compatibility,
  including the manually split Lightweight Charts chunk.

## Correctness and lifecycle

A canonical 1-minute bar beginning at `t` is not visible until
`t + 60,000 <= cursor`. Buffered future bars are excluded before data reaches
Lightweight Charts, so neither rendering, crosshair data, autoscale nor derived
timeframes can observe the future. Missing source minutes produce no candle.

Visibility suspension is not permanent user Pause. If active playback owns the
state at hide time, Replay records resumable intent, suspends at the preserved
cursor, and re-anchors before resuming when visible. Pause, import, operational
error, unavailable series, ended state, authoritative replacement and detached
ownership invalidate stale visibility intent.

Imports executed during the same App lifetime enter a barrier that pauses
Replay, clears the visible buffer, blocks stale read publication and performs
one fresh paused re-establishment after settlement. External/cross-tab mutation
detection is deliberately not claimed.

# v1.6 — Free Historical Data Foundation

Package semantic version: **1.6.0**.

Release type:
NEW CAPABILITY / ARCHITECTURAL FOUNDATION

Risk tier:
HIGH

Status:
IMPLEMENTATION, AUTOMATED VERIFICATION, AND LOCALHOST RUNTIME ACCEPTANCE
COMPLETE

Release marker:
ANNOTATED `v1.6.0` TAG

Evidence scope:
v1.6 localhost runtime acceptance was completed in a dedicated clean browser
profile against the release candidate derived from governance baseline
`3849b7a`, using the user's own local NinjaTrader exports for NQ 03-16,
ES 03-16 and NQ 06-16. Those files were never copied into the repository. Git
history is the canonical identity for the commit that carries this
implementation.

Summary:
The application can now ingest historical 1-minute futures bars, normalize them
into a provider-neutral canonical form, and store them in their own IndexedDB
database that is completely separate from journal storage. This is foundation
only: there is no Backtest UI, no chart, no replay, and no simulated trading in
this release, and nothing in the deployed application reaches this code yet.

## Why this is a new data domain

The existing feature named Backtest is filter-based analytics over trades the
user already journalled. It holds no market data, no time axis and no order
model, so historical bars had nowhere to live.

They also do not behave like journal data. A trade is authored by the user and
losing it is harm. A historical bar is an external market fact the application
keeps a copy of; losing it costs a re-import. AD-023 records that distinction as
a third data class — a reconstructable cache — and is the reason this release
adds a separate database rather than a store inside the journal's.

## What was built

- **A NinjaTrader historical adapter.** One module owns every provider-specific
  detail: the semicolon grammar, the `yyyyMMdd HHmmss` stamp, the absent header,
  the `MM-YY` expiry notation, and the End-of-Bar convention. Nothing downstream
  knows any of it. The existing trade-import CSV parser was not reused and not
  modified.
- **Deterministic timestamp normalization.** NinjaTrader exports UTC End-of-Bar
  stamps, so a 1-minute bar's canonical start is the source stamp minus exactly
  60,000 ms, covering `[start, start + 60000)`. The adapter refuses any other
  timeframe/convention pair rather than guessing.
- **Provider-neutral series identity.** A series is root, expiry year, expiry
  month and timeframe — `NQ|2016|03|1m`. No provider token appears in that
  identity, in a chunk id, in a bar, or in any read request. Provider lives only
  in import provenance.
- **Individual contracts as the stored truth.** `NQ 03-16` and `NQ 06-16` are
  separate series. Continuous and back-adjusted views are derivable later and are
  never the stored form, because that derivation only runs one way.
- **Observation-faithful storage.** A minute with no source bar has no bar.
  Nothing is filled with previous-close or zero-volume candles, and two
  instruments are never aligned by inventing a bar in one of them.
- **Atomic visibility.** Days are stored as immutable revision-bearing chunks; a
  changed day is written at the next revision, never over the committed one, and
  a single manifest write is the only operation that changes what a reader can
  see. A failed import leaves the previous state exactly as it was.
- **Serialized mutation.** On the default production path, each import, delete
  and cache clear holds one origin-wide exclusive Web Lock and re-reads state
  inside it. Without that, two concurrent imports would both target the same
  next revision and one would overwrite the other's bytes while committing its
  own provenance. The mutation APIs also expose an optional runner seam, used by
  the Node-only test harness to reach this logic, which a controlled caller can
  substitute.
- **Integrity failures fail closed.** If a manifest references a chunk that is
  proven missing, an import is rejected rather than silently rewriting that day
  with only the incoming bars — which would drop the lost data and leave a bar
  count that still counted it.
- **Fail-safe destruction.** Deleting a series writes a tombstone that hides it
  while preserving the map needed to finish cleanup after an interruption;
  clearing the cache removes manifests before payload, so a failure between the
  two leaves nothing visible and nothing reachable.
- **Failure is never mistaken for absence.** The storage layer distinguishes a
  value, a proven absence, and an operational failure, so a database error is
  reported as a read failure rather than as "this series is not here". Claiming
  absence a failed read never established would mislead the replay engine that
  will consume this data.
- **Zero-bar imports are refused outright.** An empty export cannot create a
  series with no observations, and cannot append provenance for an import that
  contributed nothing.

## What this release deliberately does not contain

No Backtest tab, chart, replay clock, layout, link system, timezone selector,
drawing tool, simulated order, or backtest-journal persistence. No chart
library. No cloud service, remote fetch, or Supabase change. No continuous
contracts, rollover engine, session calendar or holiday calendar. No tick,
one-second or bid/ask data. No NinjaTrader AddOn.

The historical modules are reachable only from source. Nothing in the deployed
application imports them, so this release adds capability without adding any
user-facing behaviour.

## Known limitations

These v1.6 Historical Data Foundation limitations remain part of the durable
historical record:

   background collector was added to eliminate residue that nothing can observe.
2. Superseded chunk revisions remain stored until the affected series is deleted
   or the historical cache is cleared.
3. Multi-year ingestion was not browser-measured during v1.6 acceptance.
4. Storage quota exhaustion was not reached during acceptance.
5. IndexedDB blocked and version-change paths were not exercised.
6. `mutation_lock_unavailable` behavior was proven by controlled injection, not
   by a naturally occurring lock failure.
7. Cross-tab evidence was one-directional rather than a full symmetric multi-tab
   concurrency proof.
8. Absence-count conclusions are limited when the original source-export window
   is unknown.

# v1.5 — Restore Integrity

Package semantic version: **1.5.0**.

Release type:
RELIABILITY / CORRECTNESS HARDENING

Risk tier:
MEDIUM

Status:
IMPLEMENTATION, AUTOMATED VERIFICATION, AND LOCALHOST RUNTIME ACCEPTANCE
COMPLETE

Release marker:
ANNOTATED `v1.5.0` TAG

Evidence scope:
v1.5 localhost functional acceptance was completed against the release
candidate derived from governance baseline `1025235`, with the implementation
surface limited to `src/components/settings/BackupPanel.tsx` and
`src/components/settings/RestorePointsPanel.tsx`. Git history is the canonical
identity for the commit that carries that implementation.

Summary:
Restoring a whole journal is now something the application asks about first,
and something the running application actually reflects afterwards. Both
whole-journal restore entry points — Restore from File and Restore Point — used
to execute on a single unconfirmed action, and a restore that succeeded left
the running app displaying and holding its pre-restore state. This release
changes when a restore is authorised and when the application re-reads storage.
It changes nothing about what a restore writes.

## The defect

`restoreBackup()` replaces up to twelve storage sections by calling each
section's existing `save()` directly. That write path is correct, and it was
never the problem. The problem was that it bypasses React entirely, while every
hook in the app persists its own in-memory snapshot whenever that snapshot
changes. After a successful restore the hooks still held the **pre-restore**
data, so the next ordinary mutation — adding, editing or deleting a single
trade — wrote that stale snapshot back over the restored data.

The consequences were silent and asymmetric. Records the restore had brought
back were destroyed, with **no tombstone, no Recovery Bin entry, and no error**,
which meant they were unrecoverable through any in-app path. Records the restore
had removed were resurrected. The Recovery Bin itself could be rewritten the
same way, in the same single action.

The only mitigation was advisory prose — a success message asking the user to
reload — with nothing enforcing it. A user restoring a backup to undo a mistake
would see a green confirmation, still see the mistake on screen, keep working,
and lose the restore.

This was reproduced at runtime on both entry points before any code changed:
with a two-trade state restored over a three-trade state, storage held the
restored two while the interface showed the pre-restore three, and one ordinary
confirmed delete then rewrote storage from stale memory.

## What changed

- **Both restore entry points now confirm first**, through the existing v1.4
  `ConfirmDialog`. Choosing a file no longer restores it; clicking Restore on a
  restore point no longer restores it. The selected payload, or the exact
  restore-point identifier, is captured into component state and the restore
  begins only on Confirm.
- **A successful restore performs one full application reload.** Hydration then
  reacquires the restored storage through the app's normal startup path, so the
  first thing the user can act on is the restored journal rather than a stale
  copy of the old one.
- **Cancel and failure never reload and never mutate.** A cancelled restore
  invokes the restore path zero times.
- **Repeated confirmation cannot execute a restore twice.** The pending payload
  is cleared and an in-flight marker is set synchronously, before anything is
  awaited, so a second click in the same tick cannot start a second restore.
- The restore-point identifier is captured once when the confirmation opens and
  is never re-derived from a list position, so sorting or list changes cannot
  re-target a confirmed restore.

## Confirmation copy

File restore:

> Restore this backup?
> This will replace your current journal data with the selected backup.
> — confirm: `Restore Backup`

Restore point:

> Restore from this point?
> This will replace your current journal data with this restore point.
> — confirm: `Restore This Point`

Both use the existing `danger` variant and the existing Cancel behaviour
(explicit button plus `Modal`'s backdrop click). No native `window.confirm`,
`window.alert` or `window.prompt` was introduced; executable occurrences in
application source remain **zero**.

## The obsolete success message

The success string `Restored {n} section(s). Reload the app to see restored
data.` was removed from both success branches. Its instruction is now performed
by the application, so keeping it would have meant rendering a false sentence
for the duration of a reload. Failure messages are unchanged: `RestoreResult`'s
own error text remains authoritative and is displayed exactly as before.

## Preserved

`services/backupService.ts` was not modified. Unchanged: restore validation;
supported backup versions; the twelve-section restore surface and its ordering;
all-or-nothing pre-write validation; unknown-key tolerance; read-back
verification; the `RestoreResult` shape; the backup JSON and restore-point
snapshot formats; restore-point creation and cap semantics; storage keys and
the authenticated user namespace; account referential validation; `RawTrade`
`_tid` identity; the Recovery Bin architecture; the Phase 29, 30, 31, 32 and
32C contracts; and the v1.4 `ConfirmDialog` contract, including its optional
`message` rule and its nested z-index of 400.

Summary:

browser. Every one of the six executable `window.confirm` flows was replaced

defect was never in the deletion code: `window.confirm()` returns `false`
immediately when the host suppresses dialogs, and every call site read that as
"the user cancelled", so a capability failure was indistinguishable from a
decision and Delete silently did nothing. This release changes confirmation
**delivery only**. Every historical deletion and recovery contract is preserved
byte-for-byte in effect, and no business logic was moved or redefined.

## The six migrated flows

1. Single Trade Delete
2. Bulk Selected Delete
3. Delete ALL
4. Recovery Bin Restore All
5. Recovery Bin Permanent Delete
6. Recovery Bin Empty Bin

Executable occurrences of `window.confirm`, `window.alert`, and `window.prompt`

## ConfirmDialog

- Application-owned React UI, composed from the **existing** `Modal` + `Button`
  atoms and the existing `COLORS` palette. No new visual language.
- **No dependency, no global provider, no context, no portal, no
  promise-returning `confirm()` shim, no destructive-action registry.**
- **No `Modal` redesign.** `Modal.tsx` was not modified.
- `message` is **optional**, and when omitted **no element is rendered** in its
  place — not an empty node.
- Severity reuses the existing `Button` variants: `danger` by default, and
  `primary` for Restore All, which is additive rather than destructive. Native
  `confirm` carried no severity styling at all, so painting that button red
  would have invented a semantic the app never had.
- Nested **z-index 400**, passed through `Modal`'s existing `zIndex` prop, so a
  confirmation opened inside Settings paints above it.
- Cancel is the explicit button **plus** `Modal`'s existing backdrop click.

# v1.3 — Manual Scale In / Out

Status:
IMPLEMENTATION + RUNTIME + LIVE VERIFICATION COMPLETE — RELEASE MARKER:
ANNOTATED `v1.3.0` TAG

Summary:
A trade can now be entered by hand as the sequence of executions it actually
was, rather than as a single entry and a single exit. An optional, collapsed
`SCALE IN / OUT (Optional)` section on the manual trade form accepts multiple
entries and partial exits, and derives the aggregate fields from those legs.
The legs are the same optional `legs` array v1.2 introduced for imported
trades — no parallel manual execution model, no migration, no storage or
backup format change. Imported NinjaTrader trades remain read-only in this
section and keep their provenance and idempotency behaviour exactly as
shipped. Trades with no legs behave precisely as before.

## Manual Scale In / Out

- New optional section on the manual trade form, **collapsed by default** and
  labelled `SCALE IN / OUT (Optional)`. A trade entered without it takes the
  unchanged v1.2 path.
- Multiple entry legs and multiple partial exit legs are supported.
- A partial exit followed by a re-entry is supported **while the position
  remains open**.
- One Journal Trade remains one completed flat-to-flat episode. A leg sequence
  that returns the position to flat before the final leg is **rejected** with a
  message naming the time it goes flat, and pointing at recording it as a
  separate trade.
- Over-exiting the open position is rejected, and total entry quantity must
  equal total exit quantity.
- Direction is chosen once on the trade and inherited by every leg; it must be
  set before legs are added.

## Editing order versus calculation order

- **Editing order is stable.** Rows do not move while a time is being typed, so
  the field under the cursor does not change identity mid-edit.
- **Canonical chronological order** is what validation, aggregate derivation
  and save use. A saved trade reopens in that canonical order.

These are deliberately two different orderings; the UI order is presentational
only and is never the arithmetic authority.

## Leg-derived aggregates

While manual legs are present they are the form's source of truth, and five
aggregate fields are derived from them rather than typed:

- `positionSize`, `entryPrice`, `exitPrice`, `entryTime`, `exitTime`.

Downstream calculations, analytics, charts, export and backup continue to read
the aggregates, unchanged.

- `positionSize` is **total entry-side transacted quantity, not peak
  simultaneous exposure**. For `Entry 2 → Exit 1 → Entry 1 → Exit 2` it is 3,
  though exposure never exceeded 2. This is the only multiplier for which
  `size × (weighted-average exit − weighted-average entry)` equals the exact
  realized difference, and it matches what v1.2 already persists for imported
  trades.
- Weighted averages are computed with **exact bigint arithmetic** — scaled
  integers and long division — never `Number`. Float64 accumulation produces
  artefacts such as `1.0834633333333335` on ordinary five-decimal forex prices.
  This reuses the technique established by the v1.2 NinjaTrader adapter without
  importing from it; that file stays frozen.

## Numeric grammar

One decimal grammar governs manual scale legs at every layer — validation,
decimal-place limits, bigint parsing, position folding and aggregate
derivation — so no two layers can disagree about what a number is.

- Forex fractional lots are accepted, including `.5`.
- Futures quantities must be **whole contracts**; fractional contracts are
  rejected.
- **Exponent notation is rejected.** `1e2`, and likewise `Infinity` and `0x1F`,
  are not valid input. `Number()` accepts these and the exact bigint layer
  cannot parse them; that validator/parser split is precisely what previously
  allowed an unparseable quantity to reach the save pipeline.
- Manual leg times are entered as `HH:mm` and persist as `HH:mm:00`. The trade
  date propagates to every manual leg.

## Provenance

- Manual legs carry **no fabricated broker provenance**. `sourceExecutionId` is
  now optional on the leg shape, and a manual leg omits the property entirely
  rather than carrying an invented digits-only ID. The absence is the
  provenance statement.
- When the property *is* present — every imported leg — it must still be a real
  digits-only string. The validation change widens the accepted set and never
  narrows it, which matters because the same validator gates backup restore:
  existing v1.2 backups restore unchanged.
- **Imported NinjaTrader legs are read-only.** The Scale section renders
  read-only whenever a source platform is present, and the save-candidate
  builder returns imported trades untouched. Imported provenance and re-import
  idempotency are preserved.

## Unchanged

- No migration. Trades with no legs remain completely valid and were not
  rewritten.
- Backup format stays at **version 2**.
- CSV export remains **aggregate-only**.
- Generic CSV/XLSX import, NinjaTrader import, Forex/CFD behaviour, analytics
  and backup/restore are otherwise unchanged.

# v1.2 — NinjaTrader Futures Import & Minimal Leg Foundation

Status:
IMPLEMENTATION + RUNTIME COMPLETE — RELEASED (tag `v1.2.0`)

Summary:
Real NinjaTrader futures activity can now be imported as logical trades. A
source-specific adapter reads a paired Executions/Trades CSV export,
reconstructs flat-to-flat position episodes, preserves the individual
executions as legs, and reconciles the complete transaction cost. Manual entry,
generic CSV/XLSX import, Forex/CFD behaviour, analytics, and backup/restore are
unchanged. Two confirmed correctness defects next to that path — AM/PM import
parsing and Arabic CSV export encoding — are repaired in the same release. No
dependency, configuration, storage-key, or backup-format change.

## NinjaTrader Futures import

- New source selector in Import/Export. **Generic CSV/Excel remains the
  default** and behaves exactly as before.
- NinjaTrader mode is **CSV only** in v1.2 and requires **both** files:
  - `Executions CSV` — supplies episode structure and the individual legs.
  - `Trades CSV` — supplies the complete cost columns, which the Executions
    export does not expose.
- Supported broker-import roots: `NQ`, `ES`, `MNQ`, `MES`. Manual Futures entry
  is unchanged and still supports every symbol in `FUT_SYMBOLS`.
- Every source account found in the files must be **explicitly mapped** to an
  active journal account. No account is silently preselected, and an unmapped
  source account aborts the import.
- Source timestamps are imported exactly as written and are assumed to be
  New York-local wall-clock time. The UI states this and requires explicit
  acknowledgement before import is enabled. No UTC or DST conversion is
  performed.
- Import is all-or-nothing. Any reconciliation mismatch, incomplete episode,
  reversal through zero, overnight episode, unsupported root, unmapped account,
  or partial re-import overlap aborts before anything is persisted.

## Logical trade semantics

One Journal Trade is one flat-to-flat position episode for the same source
account and instrument. While the position remains non-zero, all of the
following stay inside that single logical trade:

- partial fills of one order,
- intentional scale-ins placed as separate orders,
- partial exits and scale-outs.

A NinjaTrader `Trades` row is therefore not equivalent to a journal trade: one
logical trade can appear there as several rows. Import reconstructs the episode
from the executions instead.

## Leg foundation

Imported trades can preserve the underlying executions as legs, each recording
entry/exit, quantity, price, date, time to the second, and the source execution
identity. Aggregate fields remain the compatibility surface for every existing
calculation, so analytics are unaffected.

Historical and manually entered trades have no legs, remain completely valid,
and were not migrated or rewritten.

**Manual Scale In / Scale Out UI is not part of v1.2.** The data foundation
lands here; the editing UI is deferred to a later release.

## Contract identity

The original source contract is preserved (for example `MNQ SEP26`) while
calculations continue to use the root symbol (`MNQ`), which is what the
point-value table is keyed on. Storing the dated contract in the calculation
symbol would have misclassified the instrument and applied the wrong point
value.

## Fees

NinjaTrader trading cost is recorded in the existing single Commission field as
the complete set of direct costs the source provides:

`Commission + Clearing Fee + Exchange Fee + IP Fee + NFA Fee`

Historical, manually entered Commission values are unchanged and were not
corrected or recalculated.

## Correctness fixes

- **AM/PM import parsing.** `parseTime` previously matched only `H:MM` and
  discarded the meridiem, so `1:05:00 PM` silently became `01:05` and still
  passed validation. Twelve-hour input is now converted correctly
  (`12 AM → 00`, `12 PM → 12`, `1–11 PM → +12`), out-of-range values with a
  meridiem fail closed, and existing 24-hour and no-meridiem behaviour is
  byte-for-byte unchanged.
- **Arabic CSV export.** The CSV export was valid UTF-8 but carried no byte
  order mark, so Excel guessed a legacy encoding and displayed Arabic Notes as
  mojibake. `buildExportCSV` now emits a UTF-8 BOM. The export still
  re-imports into the journal with column mapping unaffected, and no historical
  file was rewritten.
- **Idempotent NinjaTrader re-import.** Re-importing the same file pair adds
  zero duplicate trades. Already-imported episodes are recognised by composite
  source provenance, so genuinely repeated trades at the same price are not
  dropped.
- **Truthful import counts.** The success message reported the number of
  episodes *discovered* as the number *imported*, so a fully-skipped re-import
  claimed work that never happened. Discovered, imported, and skipped are now
  reported separately, and the leg count refers only to newly imported trades.

- Read-only against the real NinjaTrader exports: 19 executions reconstructed

# Phase 30 — Referenced-Account Deletion Safety

Status:
COMPLETE

Summary:
Account deletion now enforces referential integrity against the current
unfiltered active raw journal. An account referenced by one or more active
raw trades cannot be deleted, so this workflow can no longer create new
orphaned active trades or send them into missing-account calculation fallback
behavior.

What shipped:
- The authoritative guard lives in `useAccounts.deleteAccount`, not only in
  Account Manager UI logic.
- App supplies the current unfiltered active `rawTrades` collection at the
  account-deletion boundary.
- Reference matching is exact: `trade.accountId === target account ID`.
- Referenced-account deletion returns a blocked result before account state,
  purge, tombstone, metadata refresh, persistence effect, or Sync mutation
  notification can be initiated.
- A blocked account and every supplied trade remain unchanged. No automatic
  trade reassignment or other trade mutation occurs.
- Existing last-active-account protection remains and is evaluated before
  target lookup or referenced-account blocking.
- Existing valid deletion behavior is preserved: never-synced accounts are
  purged locally, while previously synced accounts retain the established
  tombstone / `pending_delete` lifecycle.
- `not_found` remains non-mutating.
- `notifyLocalMutation('accounts')` runs exactly once and only after an
  authoritative successful deletion.
- AccManager interprets the deletion result only; it does not duplicate the
  reference policy.

Delete result contract:
- `{ ok: true }`
- `{ ok: false, reason: 'last_account' }`
- `{ ok: false, reason: 'referenced_by_trades' }`
- `{ ok: false, reason: 'not_found' }`
- Precedence is `last_account`, then `not_found`, then
  `referenced_by_trades`, then the existing allowed deletion lifecycle.

flushSync control flow:
- ReactDOM `flushSync` is used only at the account-deletion user-event
  boundary.
- It synchronously flushes the functional account-state update so the
  returned `DeleteAccountResult` matches the authoritative latest-state
  mutation decision.
- The bounded planner is deterministic for the account collection, target
  ID, active-trade snapshot, and externally captured operation timestamp.
- The functional updater/planner performs no external side effects.

Architectural Decisions
- Set-based idempotent callback registration (see AD-006)
- Epoch-based callback cancellation (see AD-007)
- Stamping strategy: same single implementation, two call sites, stamp
  runs before the cutover's snapshot (see AD-008)
- Source re-check strategy: Option A only, no lock (see AD-009)

Mid-Implementation Conflict (found, reported, resolved)
Initial placement called stamping immediately before the FINAL
readSource() (the re-check), per the literal first instruction. Testing
proved this unreachable for its own purpose: IndexedDB business stores
key on syncId, so an unstamped record fails the copy phase before
stamping ever runs. Reported before continuing; resolved by explicit
approval to move the call before the INITIAL snapshot instead. Re-tested
completely after the move.

  executed exactly once; Web Lock acquisitions: 1

  after stopLeaderElection() was called mid-flight
- Ordering + isolation retained after both fixes: 3 callbacks, one
  throwing, executed in registration order, later callbacks unaffected
- Unstamped legacy data (previously failed with a keyPath error):

  preserved
- Already-stamped data: completes on the first attempt, no restart
- Source re-check: a concurrent write injected mid-copy was detected;
  cutover restarted and the concurrent write is present in the final
  IndexedDB state (would otherwise have been silently lost)
- Restart path verified via the above
- Exhaustion path: source changed on every attempt -> bounded at 3 ->
  {kind:'source_changed'}, marker NOT written, LocalStorage untouched
- Stamping verified in both call sites: one implementation (stamp.ts),
