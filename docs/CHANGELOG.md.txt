## Excel / XLSX import repair

The defect:
- `components/import/ImportWizard.tsx` declared `declare const XLSX: any` and
  tested a bare GLOBAL that never existed in the migrated application. The
  original single-file app loaded XLSX from a CDN `<script>` tag; the
  migrated `index.html` has none.
- Because that ambient declaration satisfied TypeScript, `tsc` stayed at 0
  errors and the defect was invisible to typecheck. Every `.xlsx`/`.xls`
  upload fell into the "Excel library not loaded. Use CSV." branch, while
  the file input advertised `.csv,.xlsx,.xls` and the UI offered to
  "Upload any CSV/Excel file".
- Vite had been reporting the same fact on every build as
  `Generated an empty chunk: "xlsx"`.

What shipped:
- The nonexistent-global assumption is removed.
- `services/importService.ts` gains `parseWorkbookRows(data): Promise<string[][]>`,
  which loads the parser DYNAMICALLY (`await import('xlsx')`) only when an
  Excel import is actually invoked. `xlsx` was already a declared dependency
  and already had a manualChunks entry, so no dependency was added.
- The existing `read()` / `utils.sheet_to_json()` call shape is retained.
- `.xlsx` and `.xls` both continue through the same normalized `string[][]`
  pipeline that CSV uses, so `processRows()` and everything downstream are
  unchanged.
- CSV behavior is completely unchanged — it is a separate branch and
  `parseFileContent()` was not touched.
- Excel failures, including a failed chunk fetch, continue to surface through
  the existing `Excel error: ...` UI channel.
- No import envelope, DTO, adapter, or schema was introduced.

## XLSX build behavior

- A real lazy xlsx artifact is produced, measured at approximately 429 KB.
- Normal application startup does NOT fetch it: the built `index.html` does

- Main application bundle impact was small — approximately 1.3 KB.

## Persistence failure classification

- A browser `QuotaExceededError` is a `DOMException` whose identity lives on
  `.name`. The reporter classified only on `.kind` (the IndexedDb call-error

- `.name` is now consulted ONLY when no explicit `.kind` is present, so an

- The non-throwing persistence facade contract established by Release
  Hardening is unchanged.
- `LocalPersistenceNotice` was NOT modified — `quota_exceeded` was already a

## Measured SheetJS nuance

Recorded honestly, because it bounds what the Excel path guarantees:

- SheetJS does NOT throw on all malformed input. Arbitrary or unrecognized
  bytes are tolerated and read as a single-cell text sheet.
- A STRUCTURALLY broken workbook (for example a truncated ZIP container) does
  throw, and that is surfaced gracefully through the Excel error channel.
- The safety boundary for unrecognized junk is therefore downstream, not in
  the parser: such rows cannot become an import because `processRows()`
  requires a header row of more than three non-empty cells and rejects them
  with "Could not detect headers."
- It would be inaccurate to claim that all corrupt Excel files throw.

## H-1 — Persistence failure surfacing

What shipped:
- The scoped storage facade's write and remove paths no longer discard the

- The existing blocking `LocalPersistenceNotice` (§3.4) is now reachable. It
  previously could not fire at all: the scoped database wraps these writes in
  `async` methods that always RESOLVED, so the hooks' existing
  `.catch(reportLocalPersistenceFailure)` never ran. Recovery Bin, Backtests,
  saved filters, and Trade Review had no failure channel whatsoever.
- Before this change a failed write produced false success — the UI showed
  the change as saved and it was gone after the next reload.

Explicitly unchanged:
- No caller contract, storage key, namespace, schema, backup format, or
  persistence architecture change. No new notification infrastructure. No

# Phase 32C — Data Integrity and Deterministic Correctness

Status:
COMPLETE

Summary:
Active deterministic calculations no longer invent account, direction,
instrument, numeric, or date truth. New manual, imported, and restored
records are validated before persistence. Existing inconsistent historical
data stays raw and unmodified; only the affected derived values become
unavailable through the existing Phase 28 null contract.

What shipped:
- Centralized trade-content validation in a shared `tradeValidation` service
  consumed by the manual form, the import path, and restore. Account, date,
  symbol, direction, numeric, and time rules live in one place rather than
  being restated per surface.
- Import account resolution is now safe and explicit:
  - When account/broker text is absent and exactly one active account exists,
    that account is assigned.
  - When account text is present, matching is case-insensitive and exact
    against active account names; zero matches, multiple matches, and
    duplicate exact names are rejected.
  - Substring matching and first-account/`acc_1` guessing are removed.
  - Zero active accounts is a rejection, not a fallback.
  - Tombstoned accounts are not resolution candidates.
- Date handling is deterministic. Canonical `YYYY-MM-DD` and unambiguous
  slash dates are accepted; ambiguous slash dates (both components ≤ 12) and
  locale-dependent strings are left unconverted so validation rejects them.
  The browser `new Date(string)` fallback that let locale decide an
  ambiguous import's meaning is removed.
- Unsupported symbols are rejected. `findPipEntry`/`isSupportedSymbol`
  replace the generic `{ f: 1, pv: 1, t: 'forex' }` fallback on the hardened
  calculation paths, so an unknown instrument yields no invented result.
- TradeForm validates current-domain invariants before `onSave`, showing
  `Trade not saved: <reason>` and persisting nothing on failure.
- The import wizard separates accepted from rejected rows, shows a
  ready/rejected counter and a per-row rejection reason, reports
  `Imported N trades. Rejected M invalid rows.`, and refuses to import when
  no row is valid.
- Historical orphan trades — active trades referencing no active account —
  are preserved exactly. They are not reassigned, deleted, quarantined, or
  marked in storage. Only account-capital-derived values become unavailable:
  `_capital` and `_rPct` are null and no running-capital bucket is created,
  while account-independent R, points, P/L, net P/L, and risk remain
  available when their own inputs are valid. Such a trade renders
  `⚠ Unresolved account` with an explanatory tooltip.
- The historical synthetic $10,000 account-capital fallback is removed with
  no replacement number.
- Restore performs a preflight before any write: structural validation, then
  RawTrade domain validation, then effective-account referential-integrity
  validation using the backup's supplied accounts when present and the
  currently persisted accounts when omitted. An active orphan trade is
  rejected before the first save; tombstoned historical trades remain
  preservable. The portable v1/v2 backup format and version are unchanged.
- Insights hook-order safety: both hooks now run unconditionally and the
  empty-state return was moved below them, removing the two
  `react-hooks/rules-of-hooks` suppressions. Formulas, thresholds, messages,
  and populated behavior are unchanged.
- AD-017 label corrections on the surfaces that still stated a bare
  denominator: Strategy performance-table headers and the multi-filter
  comparison header now read `Win % (W/L only)`, the before/after-9:30 cards
  read `W/L win:`, the Entry Setup section reads
  `R & Win Rate (W/L only) by Entry Setup`, the Entry Setup chart series is
  `Win % (W/L only)`, and Backtest comparison reads `Win Rate (W/L only)`.
  Terminology only — no formula, threshold, or value changed.
  `AI-Powered Insights` was deliberately not renamed in this phase.

Explicitly not done:
- No Futures work, IndexedDB work, Sync/Cutover work, generalized import

- No storage key/namespace, backup format/version, schema, dependency,

# Phase 32B — Authenticated Local User Isolation

Status:
COMPLETE

Summary:
Authenticated browser-local journal persistence is now isolated by exact
authenticated user ID. Phase 32B adds a captured per-session storage scope,
an explicit and verified legacy-ownership gate, fail-closed global IndexedDB
preflight, and current-user-only Backup/Restore while leaving Sync, Cutover,
and per-user IndexedDB deferred. AD-020 records the durable architecture.

What shipped:
- The frozen 14-key logical inventory is physically namespaced as
  `fxj:user:v1:<encodeURIComponent(exactUserId)>:<logicalKey>`.
- The exact authenticated UUID is preserved without case or byte
  normalization. The exact `user.id` is also the keyed session boundary.
- Authenticated storage is captured per user/session rather than selected
  through mutable global current-user state.
- The React boundary is `AuthProvider → AuthGate → LocalOwnershipGate → keyed
  LocalOwnershipSession → UserStorageProvider → App/notice`.
- The scoped facade/database routes accounts, trades, lists, settings,
  advanced filters, Trade Review, Recovery Bin, Restore Points, Backtests,
  Backup/Restore, and the local database/stamping paths covered by Phase 32B.
- Authenticated startup no longer starts the legacy global Sync/Cutover path.
  Enabled Sync or Cutover fails closed at LocalOwnershipGate, and
  SyncConflictReview is not mounted on the authenticated scoped path.
  Dormant global compatibility accessors remain but are not reachable through
  normal authenticated business persistence.

Legacy ownership:
- Physical raw presence is authoritative. `[]`, `{}`, `null`, and
  default-looking values still count as present legacy data; malformed JSON
  under a recognized key is quarantined.
- Claim and decline are explicit. Authority has five states:
  `legacy_absent`, `legacy_detected_unclaimed`, `claim_in_progress`,
  `claim_failed_retryable`, and `claim_verified`.
- Ownership transitions are serialized by Web Locks under
  `trading-journal-ai:legacy-claim:v1`; there is no LocalStorage lease or
  polyfill fallback.
- Claim freezes a canonical SHA-256 source digest, reserves the owner, copies
  eligible data, reads it back, re-digests the preserved source, verifies the
  result, and commits/reads back `claim_verified` last. Partial residue is not
  authority, and only the reserved owner may retry or overwrite that residue.
- The legacy source is preserved after claim. An explicit wrong-user
  reservation can strand ownership pending future handling.
- The legacy Sync cursor participates in detection, snapshot, and digest, but
  remains global and is intentionally not copied. A scoped cursor starts
  absent.

IndexedDB preflight:
- The existing global `trading-journal-ai` database marker is inspected
  read-only. An absent database is not created by preflight.
- Marker presence, unsafe enumeration, or inability to read safely fails
  closed. Runtime Gate A was A1: the database was absent in the tested real
  browser profile. Broader per-user IndexedDB work remains deferred.

Backup and restore:
- Backup reads only the current authenticated scope while retaining the
  portable v1/v2 logical payload contract. Physical namespace keys and owner
  UUIDs are not exported.
- Restore Points remain scoped and excluded from portable backup. Sync cursors
  remain excluded.
- Explicit A→B portability was verified: restoring A's backup replaced B's
  disposable journal data without mutating A's namespace, while B's Restore
  Points remained B-scoped.

# Phase 24 — Recovery Factor Wiring

Status:

Summary:
Fixed a wiring defect that made the Backtest result card's "Recovery
Factor" row render "—" permanently, ever since Backtesting Foundation.

The cause was an exact inversion. computeCoreAnalytics() returns
recoveryFactor: null BY DESIGN (analytics.ts:515) — max drawdown needs
the full equity SEQUENCE, which lives in drawdown.ts, so filling it
there would create an analytics.ts <-> drawdown.ts circular import. The
field is meant to be filled afterwards by withRecoveryFactor(). But

hooks/useAdvancedAnalytics.ts:64 — a path consumed by Insights,

calculations/backtest.ts, whose result IS rendered with a Recovery

earlier. The path that renders never filled; the path that filled never
rendered.
