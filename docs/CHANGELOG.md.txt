# Phase 29 — Recovery-Complete Delete All

Status:
COMPLETE

Summary:
Delete ALL now follows the existing Recovery Bin deletion-safety workflow.
Every active raw trade targeted by the operation is captured before active
deletion is invoked, removing the one destructive trade-deletion path that
previously bypassed recovery.

What shipped:
- Delete ALL snapshots the active `rawTrades` collection and creates exactly
  one Recovery Bin entry per targeted trade.
- Recovery entries retain the original `RawTrade` payload, every raw field,
  and the original `_tid` without storing enriched projections.
- Batch entry order matches snapshot order deterministically. Every entry in
  a batch shares one operation timestamp and receives its own unique
  `nextId('recovery')` ID.
- `softDeleteMany()` appends the complete nonempty batch through one
  functional Recovery Bin state update. Empty capture is a safe no-op.
- Recovery capture invocation precedes the existing `deleteAllTrades()`
  invocation.
- Existing single-row and selected-row deletion behavior is unchanged.
- Existing Restore All is unchanged and remains compatible with the new
  batch entries and their preserved `_tid` values.
- Delete ALL confirmation now truthfully states that the trades are
  recoverable.

Exact UI copy:
"Delete ALL active trades? They will be moved to the Recovery Bin and can be restored from there."

Persistence semantics:
- Phase 29 guarantees Recovery Bin state-update invocation before active
  deletion invocation.
- It does not guarantee durable storage acknowledgment before deletion.
- Recovery Bin persistence remains best-effort through the existing effect.
- No transaction, rollback, read-back verification, retry, or persistence

- Pre-implementation review found no Recovery Bin count cap or trimming rule

# Phase 28 — Finite Derived-Number Integrity

Status:
COMPLETE

Summary:
Every derived numeric value is now finite or null. Malformed, symbolic,
blank required, and non-finite numeric operands leave raw historical
strings untouched while making affected derived values unavailable.
Valid finite calculations remain unchanged, valid zero remains zero, and
an invalid non-empty commission no longer behaves as zero commission.

What shipped:
- Finite parsing and post-arithmetic checks now protect trade enrichment,
  aggregates, running capital, equity, drawdown, Backtest snapshots,
  shared formatters, and approved page-local calculations.
- Finite aggregate arithmetic overflow becomes null; it is not clamped,
  skipped, JSON-normalized, or replaced with zero.
- Running capital cannot advance from unavailable/non-finite net P/L.
- An unavailable cumulative equity calculation returns no sequence; an
  unavailable drawdown calculation returns no DrawdownResult.
- A Backtest returns null when it cannot produce a safe immutable
  snapshot. `calculation_unavailable` remains distinct from
  `limit_reached`; a failed calculation is not appended, persisted,
  selected, or partially saved.
- The exact inline message is: "Backtest could not be calculated because
  one or more required numeric calculations were unavailable."
- Shared formatters render null, undefined, NaN, +Infinity, and -Infinity
  as `—`.
- Dashboard, Strategy, Insights, Equity, Backtest, and Calendar local
  coercion/accumulation paths are finite-safe. Unavailable values render
  or gate as unavailable without fabricated $0, 0R, 0%, neutral scores,
  comparison winners, chart points, or secondary fallback analytics.

# Phase 27 — Local Durability & Backup Integrity

Status:
COMPLETE

Summary:
Closed five local-durability gaps without changing the global storage
contract. Backup format v2 covers 12 user-data sections, including the
Recovery Bin and saved Backtest Results. Restore accepts v1 and v2,
validates every present known section before its first write, and
verifies each save by reloading through the registered load path and
comparing semantic state. Saved Backtest creation at count 50 or above
is blocked before computation instead of evicting history.

Architecture:
- Added AD-019. Saved Backtest Results now belong to Backup & Restore
  because AD-018 made new results immutable historical records;
  Recovery Bin belongs because it contains real recoverable records.
- Backtest Results remain LocalStorage-only, unsynced Class B, outside
  the resolver, IndexedDB, Sync Engine, and cutover.
- AD-019 narrowly supersedes AD-014 and AD-018 clause 4 only where they
  exclude Backtest Results from Backup & Restore, and AD-015 only where
  it requires oldest-result eviction at the 50-result cap.
- Restore remains sequential rather than transactionally atomic.

Implementation:
- `BACKUP_VERSION` is 2; only integer versions 1 and 2 are accepted.
- Backup now contains 12 sections. Recovery Bin and Backtest Results
  use their existing storage accessors. Restore Points inherit both
  through `buildBackup()`; Restore Points themselves and sync cursors
  remain excluded.
- All known sections are optional. Missing sections leave live state
  untouched; unknown sections are ignored; valid additive record fields
  are preserved. Minimum-safe validation rejects malformed present
  sections before any write without exact-schema locking or migration.
- Every non-null restored section is revived at most once, saved,
  reloaded, and compared by recursive semantic JSON equality. Detected
  save, reload, or read-back mismatch failures are surfaced, exclude the
  failed key, abort later writes, and cannot report success.
- Result #51 is blocked before `computeBacktestResult()`. Existing and
  restored collections at or above 50 are preserved without slicing,
  eviction, trimming, or migration. The page shows: "Saved Backtest
  limit reached. Delete an existing saved result before running another
  Backtest."
- Added the repository's first service/hook Node tests. No jsdom, new
  dependency, or test-configuration change was introduced.

# Phase 6g-2

Status:
COMPLETE

Summary:
Two pre-existing architectural issues from the 6g-1 audit (idempotent
callback registration, queued-callback cancellation) fixed as
initialization work, then the storage cutover itself wired end-to-end:
stamping folded into the cutover sequence (in addition to, not instead
of, the existing main.jsx call), the approved write-window mitigation
(Option A: re-read-and-restart, no lock) implemented, and the cutover
registered through startLeaderElection() behind its own independent
flag. One mid-implementation architectural conflict was found, reported,
and resolved by explicit decision before continuing (stamping order
relative to the initial snapshot).

Files Changed
- src/sync/syncEngine.ts
  - leaderCallbacks changed from Array to Set (idempotent registration by reference)
  - dispatchEpoch counter added (queued-callback cancellation on stop)
  - per-callback try/catch already present from 6g-1, retained
- src/services/storageCutover.ts
  - runSyncMetadataStampingPass() invoked immediately before the initial
    readSource() snapshot (moved here after the conflict below was
    resolved)
  - source re-check added immediately before the marker write: re-reads
    LocalStorage, compares against the original snapshot, restarts the
    whole attempt (discard -> stamp -> snapshot -> copy -> verify) on any
    difference, bounded at 3 attempts
  - new CutoverOutcome variant: 'source_changed'
- src/contexts/AuthContext.tsx
  - cutover registered via startLeaderElection(), gated on
    isStorageCutoverEnabled() and a non-null session, independent of
    isSyncEngineEnabled()
  - cutover registers before startSyncEngine() (ordering is load-bearing:
    the cutover must settle before the engine's first cycle)
  - stopLeaderElection() added to the sign-out path alongside
    stopSyncEngine()
- src/main.jsx: unchanged (explicitly preserved, per approved design)

Architectural Decisions
- Set-based idempotent callback registration (see AD-006)
- Epoch-based callback cancellation (see AD-007)
- Stamping strategy: same single implementation, two call sites, stamp
  runs before the cutover's snapshot (see AD-008)
- Source re-check strategy: Option A only, no lock (see AD-009)

Mid-Implementation Conflict (found, reported, resolved)
Initial placement called stamping immediately before the FINAL
readSource() (the re-check), per the literal first instruction. Testing
proved this unreachable for its own purpose: IndexedDB business stores
key on syncId, so an unstamped record fails the copy phase before
stamping ever runs. Reported before continuing; resolved by explicit
approval to move the call before the INITIAL snapshot instead. Re-tested
completely after the move.

Verification
- Pre-fix (idempotency): same callback reference registered 3x ->
  executed exactly once; Web Lock acquisitions: 1
- Pre-fix (cancellation): callback queued behind a slow one -> suppressed
  after stopLeaderElection() was called mid-flight
- Ordering + isolation retained after both fixes: 3 callbacks, one
  throwing, executed in registration order, later callbacks unaffected
- Unstamped legacy data (previously failed with a keyPath error):
  cutover now completes; all 4 stores stamped/wrapped; business fields
  preserved
- Already-stamped data: completes on the first attempt, no restart
- Source re-check: a concurrent write injected mid-copy was detected;
  cutover restarted and the concurrent write is present in the final
  IndexedDB state (would otherwise have been silently lost)
- Restart path verified via the above
- Exhaustion path: source changed on every attempt -> bounded at 3 ->
  {kind:'source_changed'}, marker NOT written, LocalStorage untouched
- Stamping verified in both call sites: one implementation (stamp.ts),
  two callers (main.jsx, storageCutover.ts)
- Marker-absent parity (both flags OFF, the production default):
  resolver targets LocalStorage, backupService reads/writes all 10
  LocalStorage sections unchanged, hooks hydrate and persist to
  LocalStorage, IndexedDB business counts {0,0,0,0,0}, notice silent,
  zero unhandled rejections
- Scheduler/sync regression check: coordinatorStart exactly once,
  coordinatorStop exactly once, single Web Lock acquisition even when
  registration is repeated (simulating a token-refresh re-run), cutover
  runs before the engine's first cycle, cutover-only configuration
  creates no scheduler/timer/network activity
- tsc baseline maintained: 7 errors (unchanged locations)
- Zero circular dependencies (137 files)

Known Issues (none blocking)
- Low: stopLeaderElection() cannot interrupt an already-EXECUTING
  callback (only queued ones). No abort mechanism exists in this
  codebase (AN-015 item 3); benign for the cutover since its only
  durable write is the completion marker, written solely after a
  successful copy+verify.
- Low: read failures are still labelled "save failed" in the
  local-persistence notice (carried over from 6g-1, unchanged).
- Medium: onIndexedDbBlocked still has no subscriber. More reachable now
  that the cutover is live, but still unreachable at
  DATABASE_VERSION = 1.
