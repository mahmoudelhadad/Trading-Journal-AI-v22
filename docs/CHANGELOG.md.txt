# Phase 23 — Analytics Integrity & Metric Vocabulary

Status:
COMPLETE

Summary:
Made the metric layer provable and its outputs unambiguously named,
without changing a single formula. Two slices.

Before this phase, calculations/analytics.ts (573 lines, 34 returned
fields) and calculations/rolling.ts had NO value-level test coverage —
they appeared in backtest.test.ts only as self-referential oracles
(`expect(result.summary).toEqual(summarizeTrades(matched))`), which

green/(green+red) and computeCoreAnalytics().winPct = green/n. On the
live journal the same account simultaneously displayed 26.2%, 23%, 22%
and 21.6% for what a user reads as one concept — with two of those
contradictions inside a single view.

  vitest configuration (environment: 'node'). Every expected value

  executing the function under test. The fixture makes the derivation

# Phase 22 — Global Strategy Filter

Status:
COMPLETE

Summary:
Connected the Advanced Filters capability (Phase 14) to the
application's shared trades pipeline. Before this phase a user could
build a multi-condition AND/OR filter, preview its match count, name
it, save it and favorite it — and clicking "Apply" did nothing, because
SettingsModal passed an empty function to SavedFiltersList's onApply.
A saved FilterGroup is now an active global lens that reshapes every
consuming page.

What shipped:

- GLOBAL STRATEGY FILTER. New pure L3 module calculations/
  visibleTrades.ts exporting selectVisibleTrades(trades, accFilter,
  mktFilter, activeGroup). It holds the account/market predicate moved
  VERBATIM out of useFilters.applyFilters, composed with the existing
  applyFilterGroup(). Composition order is fixed: account → market →
  group. useFilters() keeps only state and delegates; it no longer
  decides anything itself. applyFilters()'s signature is unchanged, so
  App.jsx's trades memo needed no edit.

- ACTIVE FILTER CHIP. FilterBar gained four additive optional props
  (activeFilter, visibleTradeCount, totalTradeCount,
  onClearActiveFilter) rendering the filter name, an "N of M trades"
  count and a ✕ clear control. Deliberately NOT labelled "N matches":
  the number is account ∩ market ∩ group, a different quantity from
  the group's own match count shown by FilterPanel's builder preview.

- SNAPSHOT SEMANTICS. Applying stores structuredClone(f.group) plus
  the filter's name and sourceId. Deleting or editing the source
  SavedFilter afterwards cannot change what the user is viewing.

- BACKTEST ISOLATION. pages/Backtest.tsx still receives UNFILTERED
  allTrades. A globally-filtered Backtest would silently break every
  stored result's self-describing contract. Verified statically and by
  runtime measurement.

- SAVED FILTERS. SavedFiltersList's Apply is now live via a new
  optional SettingsModal prop onApplyFilter, forwarded from App.jsx,
  which sets the lens and closes the modal. The prop is optional, so
  omitting it reproduces the previous inert behavior exactly.

- EMPTY-STATE BEHAVIOR. A filter matching nothing renders the chip as
  "0 of M trades" — the chip never hides itself — and every page falls
  back to its own empty state. Confirmed with no crashes and no
  console errors.

- CLEAR IS SCOPED. clearActiveFilter() removes the active group only;
  the account and market filters are untouched.

Two pre-existing architectural issues from the 6g-1 audit (idempotent
callback registration, queued-callback cancellation) fixed as
initialization work, then the storage cutover itself wired end-to-end:
stamping folded into the cutover sequence (in addition to, not instead
of, the existing main.jsx call), the approved write-window mitigation
(Option A: re-read-and-restart, no lock) implemented, and the cutover
registered through startLeaderElection() behind its own independent
flag. One mid-implementation architectural conflict was found, reported,
and resolved by explicit decision before continuing (stamping order
relative to the initial snapshot).

  - leaderCallbacks changed from Array to Set (idempotent registration by reference)
  - dispatchEpoch counter added (queued-callback cancellation on stop)

Architectural Decisions
- Set-based idempotent callback registration (see AD-006)
- Epoch-based callback cancellation (see AD-007)
- Stamping strategy: same single implementation, two call sites, stamp
  runs before the cutover's snapshot (see AD-008)
- Source re-check strategy: Option A only, no lock (see AD-009)

Mid-Implementation Conflict (found, reported, resolved)
Initial placement called stamping immediately before the FINAL
readSource() (the re-check), per the literal first instruction. Testing
proved this unreachable for its own purpose: IndexedDB business stores
key on syncId, so an unstamped record fails the copy phase before
stamping ever runs. Reported before continuing; resolved by explicit
approval to move the call before the INITIAL snapshot instead. Re-tested
completely after the move.

Verification
- Pre-fix (idempotency): same callback reference registered 3x ->
  executed exactly once; Web Lock acquisitions: 1
- Pre-fix (cancellation): callback queued behind a slow one -> suppressed
  after stopLeaderElection() was called mid-flight
- Ordering + isolation retained after both fixes: 3 callbacks, one
  throwing, executed in registration order, later callbacks unaffected
- Unstamped legacy data (previously failed with a keyPath error):
  cutover now completes; all 4 stores stamped/wrapped; business fields
  preserved
- Already-stamped data: completes on the first attempt, no restart
- Source re-check: a concurrent write injected mid-copy was detected;
  cutover restarted and the concurrent write is present in the final
  IndexedDB state (would otherwise have been silently lost)
- Restart path verified via the above
- Exhaustion path: source changed on every attempt -> bounded at 3 ->
  {kind:'source_changed'}, marker NOT written, LocalStorage untouched
- Stamping verified in both call sites: one implementation (stamp.ts),
  two callers (main.jsx, storageCutover.ts)
- Marker-absent parity (both flags OFF, the production default):
  resolver targets LocalStorage, backupService reads/writes all 10
  LocalStorage sections unchanged, hooks hydrate and persist to
  LocalStorage, IndexedDB business counts {0,0,0,0,0}, notice silent,
  zero unhandled rejections
- Scheduler/sync regression check: coordinatorStart exactly once,
  coordinatorStop exactly once, single Web Lock acquisition even when
  registration is repeated (simulating a token-refresh re-run), cutover
  runs before the engine's first cycle, cutover-only configuration
  creates no scheduler/timer/network activity
- tsc baseline maintained: 7 errors (unchanged locations)
- Zero circular dependencies (137 files)

Known Issues (none blocking)
- Low: stopLeaderElection() cannot interrupt an already-EXECUTING
  callback (only queued ones). No abort mechanism exists in this
  codebase (AN-015 item 3); benign for the cutover since its only
  durable write is the completion marker, written solely after a
  successful copy+verify.
- Low: read failures are still labelled "save failed" in the
  local-persistence notice (carried over from 6g-1, unchanged).
- Medium: onIndexedDbBlocked still has no subscriber. More reachable now
  that the cutover is live, but still unreachable at
  DATABASE_VERSION = 1.
