## Referenced-Account Definition

A reference is an active trade from App's current unfiltered `rawTrades`
collection whose persisted/raw `accountId` strictly equals the target
account ID:

`trade.accountId === target account ID`

The population excludes trade tombstones, Recovery Bin snapshots, backups,
Restore Points, saved Backtest IDs, remote-only records, and filtered or
enriched trade projections.

---

## Authoritative Guard Boundary

The implemented ownership flow is:

1. App owns current active `rawTrades` and active accounts.
2. App passes `rawTrades` to `useAccounts.deleteAccount` at deletion time.
3. `useAccounts` evaluates the deletion decision against the latest account
   state inside its functional state updater.
4. AccManager only interprets the returned result.

Neither App nor AccManager duplicates the account-reference policy. No new
service, provider, global state, or production helper file was introduced.

---

## DeleteAccountResult Contract

Supported results are exactly:

- `{ ok: true }`
- `{ ok: false, reason: 'last_account' }`
- `{ ok: false, reason: 'referenced_by_trades' }`
- `{ ok: false, reason: 'not_found' }`

Every failure is non-mutating and returns the original account-state
collection from the planner.

---

## Last-Account Precedence

Decision order is:

1. `last_account`
2. `not_found`
3. `referenced_by_trades`
4. existing valid deletion lifecycle

If the sole active account is referenced, `last_account` wins. The existing
hidden Delete button and hook-level protection remain unchanged.

---

## flushSync Control Flow

- ReactDOM `flushSync` is localized to the Account Manager deletion
  user-event boundary.
- One operation timestamp is captured outside the updater.
- The functional updater runs the bounded deterministic planner against its
  latest `prev` account collection.
- A blocked plan returns the original `prev`; an allowed plan constructs the
  established purge-or-tombstone next state.
- The synchronous `DeleteAccountResult` therefore matches the authoritative
  updater decision.
- The updater/planner performs no external side effects.
- `notifyLocalMutation('accounts')` remains outside the updater and executes
  exactly once only after an actual successful deletion.
- `flushSync` is not used elsewhere as a general state-management pattern.

## Known Risks / Limitations

- Phase 30 prevents only this account-deletion workflow from creating new
  orphaned active trades.
- It does not repair orphaned trades that may already exist from historical
  data, old backups, imports, or previous application behavior.
- The synthetic $10,000 missing-account capital fallback remains unchanged.
- Zero and negative account-capital behavior remains unchanged.
- The authoritative trade population is App's current unfiltered active
  `rawTrades` collection.
- Authenticated behavior was not directly observed in a disposable account.
- Existing orphan repair, authenticated local-user isolation, Insights
  correctness, AD-017 vocabulary completion, Trade Review activation,
  Futures import, and Sync/cutover readiness remain separate work.
