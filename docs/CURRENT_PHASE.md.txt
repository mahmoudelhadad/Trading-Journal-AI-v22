## Phase

Phase 24 — Recovery Factor Wiring

Status:

COMPLETE

---

## Objective

Make newly computed BacktestResult objects populate core.recoveryFactor
by calling the already-existing, already-tested withRecoveryFactor()
helper, using the drawdown computeBacktestResult() already computes.

Before this phase the Backtest result card's "Recovery Factor" row
rendered "—" permanently, and had done since Backtesting Foundation.

---

## Scope (as delivered)

1. calculations/backtest.ts — four lines. The analytics import was
   extended to include withRecoveryFactor; the existing inline
   computeDrawdown(equitySequence) call was hoisted into a single
   `const drawdown`; that same object is returned by shorthand; and
   `core` is now
   withRecoveryFactor(computeCoreAnalytics(matched),
                      drawdown.maxDrawdownDollar).
   computeDrawdown() is still called exactly ONCE, so the value feeding
   recoveryFactor and the value stored in result.drawdown are the same
   object and cannot diverge.
2. calculations/backtest.test.ts — T-2 and T-3 added BEFORE the
   production change; T-1's existing oracle updated to the composed
   form afterwards.

Nothing else. No formula, no type, no storage, no migration.

## Known Risks

Introduced by this phase:

- Low: calculations/backtest.ts's file header enumerates the L3
  functions it composes and does not mention withRecoveryFactor(), so
  that list is now incomplete. Documentation drift inside a production
  file. Correcting it would have been a fifth edit to backtest.ts beyond
  the four the frozen RFC authorised, so it was recorded rather than
  taken as an unapproved scope expansion. Safe to fix in any future
  phase that legitimately opens this file.
- Low: the fix does not guarantee a visible value. A backtest whose
  matched set never draws down still yields recoveryFactor null and
  still renders "—". Pinned by T-3.

Carried forward, unchanged and unrelated:

- Low/Medium: fixed-threshold analyses (pages/Insights.tsx) run against
  arbitrarily small filtered samples with no minimum-sample guard. Only
  1 of 13 rules gates on total n; 5 gate on an inlined per-group n >= 2
  duplicated three times; 5 have no guard at all. Insights.tsx:271
  already promises "need at least 5 trades", a minimum nothing enforces.
  This is Phase 25's subject.
- Low: rule 12's avgR / avgPlanned type selector misbehaves when
  avgPlanned is 0 or negative, while its body defensively prints 0%; and
  its avgR !== null guard is dead.
- Low: the same all-trades quantity renders as 22% on Insights
  (Math.round) and 21.6% in the Backtest table (fr.pct, toFixed(1)) — a
  display precision difference, not a formula or denominator difference.
- Low: getWinLossBreakdown's `closed` means DECISIVE, not closed;
  payoffRatio also returns null when avgLoserDollar is exactly 0;
  avgCommission's parseFloat tolerance; getWeekKey's timezone
  dependency at UTC offsets >= +12 or <= -12.
- Low: the FilterBar chip's "N of M" denominator is the total
  unfiltered count (Phase 22).
- Medium: onIndexedDbBlocked has no subscriber (G-3, Phase 6h).
  Unreachable at DATABASE_VERSION = 1, confirmed still 1.
- Low/Medium items from Phase 6g-2/6h.
- The 7 pre-existing lint warnings.
