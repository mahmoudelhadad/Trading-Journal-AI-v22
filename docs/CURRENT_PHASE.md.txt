# Current Phase

## Phase

Phase 27 — Local Durability & Backup Integrity

Status:

COMPLETE

---

## Objective

Prevent silent or misleading local-data loss for records the application
presents as saved, recoverable, or historical. Validate backup contents
before mutation, make restore persistence failures observable, include
Recovery Bin and saved Backtest Results in backup snapshots, and stop the
50-result cap from silently evicting history.

---

## Scope (as delivered)

- Backup format v2 emits 12 centralized user-data sections.
- Restore accepts versions 1 and 2 only and rejects invalid or unsupported
  versions before writes.
- Recovery Bin and saved Backtest Results are included in Backup & Restore.
- Restore Points inherit both datasets through `buildBackup()`; Restore
  Points themselves and sync cursors remain excluded.
- Every present known section receives minimum-safe, additive-tolerant
  validation before the first save. Missing sections leave live state
  untouched; unknown sections are ignored; unknown valid fields survive.
- Each non-null section is revived at most once, saved through its
  registered path, reloaded through that same path, and compared by
  semantic JSON-state equality. Detected persistence failure is surfaced,
  aborts later sections, and cannot report success.
- Saved Backtest creation at count 50 or greater is blocked before
  computation. Existing and restored results are never sliced, evicted,
  trimmed, migrated, or deleted by the cap.
- The Backtest page renders the approved inline guidance when creation is
  blocked. Manual deletion immediately frees capacity once the count falls
  below 50; rename behavior is unchanged.
- The global `storageSet` contract remains unchanged.

- Authenticated UI paths were not directly observed during disposable
  runtime verification.
