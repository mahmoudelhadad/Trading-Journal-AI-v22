## Objective

Make the visible Delete ALL trade action follow the existing Recovery Bin
deletion-safety workflow so it no longer uniquely bypasses recoverable
deletion while single-row and selected-row deletion remain recoverable.

Phase 29 provides parity with existing Recovery Bin semantics. It does not
introduce stronger persistence guarantees.

## Recovery Contract

- Delete ALL snapshots every currently active `RawTrade` targeted by the
  operation.
- Exactly one new Recovery Bin entry is created per targeted active trade.
- The original raw object/data and every raw field are retained; no enriched
  projection is stored.
- Original `_tid` values are preserved exactly.
- No captured trade is omitted or duplicated within the new batch.
- Empty input creates no Recovery Bin entries.
- The persisted Recovery Bin entry schema and storage key are unchanged.

---

## Batch Semantics

- `RecoveryBinCapture<T>` contains only `item` and `label`.
- Entry construction receives one operation timestamp and one unique
  `nextId('recovery')` result per capture.
- Every entry in one batch shares the operation timestamp.
- Entry order matches snapshot/capture order deterministically.
- `softDeleteMany()` appends all new entries through one functional Recovery
  Bin state update rather than N independent updates.
- Existing `softDelete(item, label)` retains its public behavior and produces
  the established single-entry shape.

---

## Delete Ordering

The implemented order is:

1. Snapshot current active `rawTrades`.
2. Map the snapshot to Recovery captures in snapshot order.
3. Invoke `softDeleteMany(captures)`.
4. Invoke the existing `deleteAllTrades()` lifecycle.
5. Preserve TradeTable's existing selection-clearing behavior.

Recovery state-update invocation precedes active deletion invocation. This
ordering is not a durable storage acknowledgment.

---

## Exact Confirmation Wording

"Delete ALL active trades? They will be moved to the Recovery Bin and can be restored from there."

The wording intentionally makes no promise about cloud backup, Sync,
automatic Restore Points, or durability under storage failure.

## Persistence Limitation

Recovery Bin persistence remains best-effort through the existing effect.
Phase 29 guarantees only that Recovery Bin state-update invocation occurs
before active deletion invocation. It does not wait for or verify a durable
storage write.

Storage quota, browser-storage denial, or another persistence failure can
therefore still prevent durable Recovery Bin capture. This limitation was
not redesigned or strengthened.

Pre-implementation retention review found no count cap or trimming rule
capable of immediately truncating the newly captured Delete ALL batch. New
batch entries share a current timestamp and are not immediately expired by
the existing 30-day age policy.
