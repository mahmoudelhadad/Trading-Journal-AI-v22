## Objective

Make a whole-journal restore an explicit, confirmed replacement that the running
application actually reflects afterwards, while preserving every existing
restore, backup and storage contract exactly.

v1.5 changes **when a restore is authorised** and **when the application
re-reads storage**. It changes nothing about what a restore writes.

---

## Frozen Invariant

A restore is an explicit, confirmed, complete replacement of local state. It
does not begin without the user's confirmation. Once a restore succeeds, the
running application reacquires the restored state before the user can continue
mutating the journal. A failed or cancelled restore does not reload and does not
mutate data.

---

## The Defect This Closes

`restoreBackup()` replaces up to twelve storage sections through each section's
existing `save()`. That write path was correct and was never the defect. It
bypasses React entirely, while every hook persists its own in-memory snapshot
whenever that snapshot changes — so after a successful restore the hooks still
held the **pre-restore** data, and the next ordinary mutation wrote that stale
snapshot back over the restored data.

Records the restore had brought back were destroyed with no tombstone, no
Recovery Bin entry and no error, leaving them unrecoverable through any in-app
path. Records the restore had removed were resurrected. The Recovery Bin could
be rewritten the same way in the same action. The only mitigation was an
advisory success message asking the user to reload, with nothing enforcing it.

The defect was reproduced at runtime on both entry points before any code
changed.

---

## Delivered Scope

1. **Confirmation before replacement.** Both whole-journal restore entry points
   render the existing v1.4 `ConfirmDialog`. Selecting a backup file does not
   restore it; clicking Restore on a restore point does not restore it. The
   payload, or the exact restore-point identifier, is captured into component
   state and the restore begins only on Confirm.

2. **Success-only reload.** A successful restore performs exactly one full
   application reload, so hydration reacquires the restored storage through the
   normal startup path before the user can mutate anything.

3. **Cancel and failure are inert.** Zero restore invocations, zero storage
   mutation, zero reloads.

4. **Double-submit prevention.** The pending payload is cleared and an in-flight
   marker set synchronously, before anything is awaited, so repeated
   confirmation cannot start a second restore.

5. **Exact restore-point capture.** The identifier is captured once when the
   confirmation opens and never re-derived from a list position.

6. **Obsolete success copy removed.** `Restored {n} section(s). Reload the app
   to see restored data.` was removed from both success branches; the
   application now performs that instruction itself.

testing library, or production seams existing purely for mocking would have been
a larger and less honest change than the fix. Static inspection and runtime
acceptance carry this evidence, and the limitation is recorded rather than
concealed.

- Successful restores reloaded automatically **exactly once**, and after
  hydration the interface matched persisted storage, with no manual refresh
  performed at any point.
- **Double-submit proof:** five synchronous confirmation clicks on one opened
  dialog produced exactly one restore pass — twelve section writes and one
  reload — on both entry points.

  the middle row restored exactly that point's three-trade payload, neither the
  two-trade nor the four-trade neighbour; a second run from the top row restored
  exactly its own four-trade payload.
- **The baseline data-loss sequence was specifically re-tested after the fix.**
  Following an automatic reload from a restored three-trade state, one ordinary
  confirmed delete left exactly the restored set minus the deleted trade: the
  restored trade absent from the stale snapshot **survived**, the trade removed
  by the restore did **not** resurrect, and the Recovery Bin received exactly
  one entry.
- With `confirm`, `alert` and `prompt` instrumented to record across the reload,
  both paths reported zero native invocations; the primitives were verified
  native afterwards.
- Post-reload smoke passed: every page rendered, Settings and Recovery Bin

A successful whole-journal restore is a deliberate destructive replacement, so

this scope: the action is confirmed first, and retaining stale in-memory state
is exactly the defect being closed.

Two historical contracts remain deliberately deferred and were not reopened:
**deletion does not automatically create a backup or restore point**, and
**transactional / durable-ack deletion remains intentionally deferred.**

## Architecture Decision

**No new ADR was recorded, and `docs/ARCHITECTURE_DECISIONS.md.txt` was not
modified.**

Confirmation plus a success-only full reload is a bounded UI and lifecycle
correction that uses the application's **existing** hydration and storage
authority. It introduces no cross-cutting invalidation authority, no rehydration
event system, no new storage abstraction and no new module boundary — it changes
only when the application re-enters a startup path it already had. The existing
ADR set was reviewed and none of AD-001 through AD-022 governs restore
confirmation or post-restore state reacquisition.

The reload primitive itself follows existing repository practice: a direct
`window.location.reload()` call in a component, as already used by
`src/components/ErrorBoundary.tsx` and `src/components/LocalPersistenceNotice.tsx`.

## Known Limitations

Non-blocking. None of these is a release blocker.

P2:
- Confirm/Cancel click wiring, the success-only reload condition, and
  post-restore reacquisition are not covered by automated tests, because the
  Node-only harness cannot reach them. Runtime acceptance is the evidence, and
  no test architecture was added to manufacture coverage.
- Destructive actions outside the two restore paths and the six flows migrated
  in v1.4 still have no confirmation: account delete, restore-point delete,
  saved-filter delete, checklist and custom-field delete, List reset, and
  General Settings reset.
- Externally malformed data carrying `sourceExecutionId` without a
  `sourcePlatform` is not specifically classified (carried from v1.3).

P3:
- Escape does not dismiss a restore confirmation; Cancel and backdrop click are
  the dismissal paths, matching the rest of the v1.4 confirmation surface.
- A successful restore's reload discards transient unsaved interface state, such
  as an open trade form. This is accepted and deliberate for a confirmed
  destructive replacement.
- A stale JSDoc comment in `src/hooks/useTrades.ts` still names `window.confirm`.
  Its substantive claim — that confirmation is a UI-layer concern — remains
  true. The file stayed outside this release's frozen surface.
- Narrow/mobile visual coverage of the Scale section is partial (from v1.3).
- Externally malformed manual leg seconds other than `:00` are tolerated rather
  than rejected (from v1.3).
- Removing every leg from a never-saved trade can leave the unlocked aggregate
  fields blank (from v1.3).
- A pre-existing `Trade not saved` message can persist until the next save
  (from v1.3).
