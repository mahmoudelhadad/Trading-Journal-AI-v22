## Objective

Replace the six executable browser-native `window.confirm` destructive flows
with application-owned React confirmation UI, while preserving every existing
deletion and recovery business contract exactly.

The defect this closes was recorded as a v1.3 known limitation: a browser
configured to suppress dialogs silently disabled deletion. `window.confirm()`
returns `false` immediately when the host suppresses dialogs, and every call
site treated that as "the user cancelled" — so a capability failure was
indistinguishable from a decision. The deletion code itself was never broken.

v1.4 changes confirmation **delivery only**.

---

## Delivered Scope

1. **`ConfirmDialog`** — a bounded, application-owned React confirmation
   component composed from the existing `Modal` + `Button` atoms and the
   existing `COLORS` palette. No dependency, no provider, no context, no
   portal, no `confirm()` shim, no destructive-action framework, and no `Modal`
   redesign.

2. **Six migrated flows** — Single Trade Delete, Bulk Selected Delete, Delete
   ALL, Recovery Bin Restore All, Recovery Bin Permanent Delete, Recovery Bin
   Empty Bin.

3. **Zero native dialog primitives** in these paths. Executable occurrences of
   `window.confirm`, `window.alert`, and `window.prompt` in application source
   are now zero. The primitive was removed, not wrapped or relocated.

4. **Bulk ID snapshot at dialog-open time**, so the confirmed count and the
   acted-upon set are provably the same list. This preserves an atomicity
   guarantee that `window.confirm`'s synchronous blocking previously supplied
   for free.

5. **One authorized copy correction** — the bulk-delete confirmation no longer
   claims "This cannot be undone."

## ConfirmDialog Contract

- `title` (required), `message` (**optional**), `confirmLabel` (required),
  `onConfirm`, `onCancel`, `confirmVariant` (`danger` default, or `primary`).
- When `message` is omitted, **no element is rendered in its place** — not an
  empty node.
- Severity reuses the existing `Button` variants. `primary` exists solely
  because Restore All is additive rather than destructive; native `confirm`
  carried no severity styling, so red would have invented a semantic the app
  never had.
- Nested **z-index 400**, via `Modal`'s existing `zIndex` prop.
- Cancel is the explicit button plus `Modal`'s existing backdrop click. Escape
  handling was deliberately not added, since that requires changing the shared
  `Modal`.
- Callers render conditionally; there is no `open` prop.

## Preserved Historical Contracts

**Single Delete** — one confirmation; Cancel mutates nothing; Confirm invokes
the existing soft-delete path unchanged.

**Bulk Selected Delete** — exactly one confirmation per batch, never N; IDs
snapshotted at dialog-open time; every selected trade remains recoverable;
selection preserved on Cancel and cleared after Confirm.

**Delete ALL** — population is **all active `rawTrades`**, never the filtered
or visible rows; **no count in the confirmation**; the Phase 29 snapshot,
order, `_tid`, and `softDeleteMany` contracts are untouched. The dialog holds
no trade context at all, which is what makes the filtered view structurally
incapable of influencing the deleted population.

**Restore All** — existing ordering, original `_tid`, and the one existing
`importTrades()` reinsertion path.

**Permanent Delete / Empty Bin** — Phase 31 exactly-once on Confirm and
zero-on-Cancel semantics preserved; permanent delete passes the same captured
Recovery entry ID; neither path mutates active trades; historical wording
preserved.

## Copy Correction

Exactly one historical confirmation string was intentionally changed.

- Old bulk message: `This cannot be undone.`
- New truth: the selected trades are moved to the Recovery Bin and can be
  restored from there.

The Delete ALL and Recovery Bin strings are preserved exactly — each is split
across the dialog's title and message at its existing sentence boundary and
reconstructs the original string character-for-character. Single Delete and
Restore All keep their historical question text with no message added.

## Architecture Decision

**No new ADR was recorded, and `docs/ARCHITECTURE_DECISIONS.md.txt` was not
modified.**

v1.4 replaces a browser-native confirmation delivery primitive with an
application-owned React component while deliberately preserving every existing
deletion and recovery business contract. It changes no deletion architecture,
no Recovery architecture, no storage, schema, or namespace, no backup format,
no Restore semantics, no `_tid` identity, no Delete ALL population semantics,
no transactional durability posture, and no automatic backup policy.

`ConfirmDialog` is a bounded UI implementation choice with a local prop
contract used at six call sites and carrying zero business logic — not a new
cross-cutting architectural authority. The existing ADR set was reviewed and
none of AD-001 through AD-022 governs confirmation delivery.

---

## Migration Impact

None. No storage key, namespace, schema, or backup format version change. No
historical data was rewritten and no trade was migrated. The change is confined
to how a user's confirmation decision is captured.

## Known Limitations

Non-blocking. None of these is a release blocker.

P2:
- Destructive actions **outside** the six migrated flows still have no
  confirmation at all: account delete, restore-point delete and restore,
  backup-file restore, saved-filter delete, checklist and custom-field delete,
  and List reset. These were explicitly out of v1.4 scope.
- There is no full DOM-level integration harness; Confirm/Cancel click wiring
  is not automatically tested, because the harness is Node-only with no DOM.
  Runtime acceptance is the evidence, and no fake event framework was added.
- Externally malformed data carrying `sourceExecutionId` without a
  `sourcePlatform` is not specifically classified (carried from v1.3).

P3:
- Escape does not dismiss a confirmation; Cancel and backdrop click are the
  dismissal paths.
- A stale JSDoc comment in `src/hooks/useTrades.ts` still names
  `window.confirm`. Its substantive claim — that confirmation is a UI-layer
  concern — remains true. The file is outside the frozen v1.4 manifest and was
  deliberately not edited; this is a deferred documentation cleanup.
- Narrow/mobile visual coverage of the Scale section is partial (from v1.3).
- Externally malformed manual leg seconds other than `:00` are tolerated rather
  than rejected (from v1.3).
- Removing every leg from a never-saved trade can leave the unlocked aggregate
  fields blank (from v1.3).
- A pre-existing `Trade not saved` message can persist until the next save
  (from v1.3).
