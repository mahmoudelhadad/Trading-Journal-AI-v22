Phase 23 — Analytics Integrity & Metric Vocabulary

Status:

COMPLETE

## Objective

Make the metric layer provable and its outputs unambiguously named,
without changing a single formula.

Two problems, both live and user-visible before this phase:

1. calculations/analytics.ts (573 lines, 34 returned fields) and
   calculations/rolling.ts had NO value-level test coverage. They
   appeared in backtest.test.ts only as self-referential oracles
   (`expect(result.summary).toEqual(summarizeTrades(matched))`), which
   proves composition but never a value. summarizeTrades() is the
   most-called calculation in the application.

2. Two different quantities reached the user under the identical label
   "Win Rate": summarizeTrades().wr = green/(green+red) and
   computeCoreAnalytics().winPct = green/n. The divergence has been
   documented in analytics.ts since Phase 8; the label collision never
   was. Two surfaces contradicted themselves inside a single view —
   the Dashboard KPI against its own outcome pie, and the Backtest
   result card's KPI against its own table.

## Scope (as delivered)

SLICE 1 — Characterization tests, purely additive:

1. calculations/rolling.test.ts (new) — summarizeTrades (all 9 fields,
   empty baseline, all-Breakeven, all-blank, null-field handling),
   groupTradesBy (bucketing, falsy-key exclusion, key stringification),
   aggregateByPeriod ('day' and 'month' fully; 'week' shape, sort and
   conservation only).
2. calculations/analytics.test.ts (new) — getWinLossBreakdown, the full
   34-field empty-input baseline, the 29 Class-A fields of
   computeCoreAnalytics with their null/empty edges, the daily rollup,
   the risk/quality scores, the undefined-denominator cases,
   withRecoveryFactor, and the Class-C aliases as identity assertions
   only.
3. The divergence guard — winPct !== wr on a set containing Breakeven
   and blank outcomes, both values pinned exactly, plus a sibling
   asserting they agree when every trade is decisive.

Every expected value was hand-derived from the documented FORMULA
blocks. None was produced by executing the function under test.

SLICE 2 — Metric label disambiguation, text only (L-1..L-6):

4. Dashboard KPI -> "Win Rate (W/L only)".
5. Insights StatBox -> "Win Rate (all trades)".
6. Backtest result KPI -> "Win Rate (W/L only)".
7. Backtest core table -> "Win % (all trades)", "Loss % (all trades)",
   "Breakeven % (all trades)".
8. Insights rule titles -> "Strong All-Trade Win Rate",
   "Low All-Trade Win Rate (N%)".
9. Insights good-rule body -> "All-trade win rate N% ...".

The Dashboard outcome pie legend is deliberately unchanged (RFC open
question OQ-2, approved): it is a composition display in a card already
titled "Win / Loss / BE", not a win-rate label.

## Known Risks

Introduced by this phase:

- Low: L-6's renamed good-rule body is diff-verified only. The diff
  shows a single string literal changed with the embedded expression
  byte-identical, typecheck is clean, and its sibling branch in the
  same if/else is confirmed rendering correctly by V-15 — but the
  branch itself has not been seen at runtime.
- Low: two names now exist for what users colloquially call one thing.
  A future metric or narration layer must choose deliberately. AD-017
  exists so that choice is made against a written vocabulary.

Confirmed during this phase, PRE-EXISTING and explicitly deferred —
not regressions:

- Medium: the Backtest result card's "Recovery Factor" row renders "—"
  permanently. calculations/backtest.ts calls computeCoreAnalytics()
  without withRecoveryFactor(), whose only call site is
  hooks/useAdvancedAnalytics.ts; conversely the three pages where it IS
  computed never read it. Observed live during V-12. Phase 23 pins the
  current behavior with an identity assertion and does not fix it.
- Low: the same all-trades quantity renders as 22% on Insights
  (Math.round) and 21.6% in the Backtest table (fr.pct, toFixed(1)).
  A display PRECISION difference, not a formula or denominator
  difference.
- Low: getWinLossBreakdown's `closed` means DECISIVE, not closed — a
  Breakeven trade is closed in the ordinary sense but is excluded.
  Four metrics key off this name.
- Low: payoffRatio also returns null when avgLoserDollar is exactly 0;
  undocumented.
- Low: avgCommission uses parseFloat, so "12abc" is included as 12,
  contradicting its doc's "non-numeric ... excluded".
- Low, environment-dependent: getWeekKey builds a LOCAL date from
  `${dateStr}T12:00` then reads toISOString(). At UTC offsets >= +12 or
  <= -12 the Monday-start key lands on the wrong day. The 'week' test
  deliberately asserts shape and sort only, so this behavior is not
  frozen.

Carried forward, unchanged and unrelated:

- Low/Medium: fixed-threshold analyses (pages/Insights.tsx) still run
  against arbitrarily small filtered samples with no minimum-sample
  guard (Phase 22).
- Low: the FilterBar chip's "N of M" denominator is the total
  unfiltered count (Phase 22).
- Medium: onIndexedDbBlocked has no subscriber (G-3, Phase 6h).
  Unreachable at DATABASE_VERSION = 1, confirmed still 1.
- Low/Medium items from Phase 6g-2/6h.
- The 7 pre-existing lint warnings.
